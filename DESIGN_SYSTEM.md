# Konomi design system

Human-readable reference for the token set defined in [`src/lib/konomi/tokens.ts`](src/lib/konomi/tokens.ts) and [`src/lib/konomi/themes.ts`](src/lib/konomi/themes.ts), mirrored as CSS custom properties in [`src/app/globals.css`](src/app/globals.css). Those three files are the single source of truth — this document is a snapshot of what they currently contain, not a second copy to maintain by hand.

**`disabledBg` and `slotEmpty` are the same value in every theme, deliberately** — the recommend button's disabled state and an empty drop-tag slot are the same "nothing here yet" surface, and should read as one visual language, not two unrelated grays that happen to both mean "inactive." Which token supplied the shared value differed per theme, picked by whichever one already read correctly against that theme's `bg`: default and third kept their existing `slotEmpty` (each already a proper faded tint of `surface`) and brought `disabledBg` in line with it; dark did the reverse — its old `slotEmpty` (`#1B2329`) sat almost on top of `bg` (`#12181C`) and was effectively invisible, while `disabledBg` (`#243038`) was already a properly distinct surface, so `slotEmpty` was brought in line with that instead. `TagSlot`'s empty state already read `--slot-empty` directly, and the badge's filled states already read `--fill` (the same token `Random ×3` uses) — no component code needed to change for either half of this alignment, only the token values themselves.

**The `X / 3` badge's *text* color carries the same zero/filled distinction as its background, not just `--ink` throughout.** Once `slotEmpty`/`disabledBg` converged (above), the badge's bg alone was too subtle a signal in the darker themes — a small box bordered and labeled in `--ink` read as roughly the same box regardless of state, because the text dominated more of its area than the background. `MixerBar`'s badge now pairs `--disabled-text` with the bg at `0/3` (matching `RecommendButton`'s own disabled label color) and `--ink` with the bg from `1/3` up (matching `Random ×3`/`Clear ✕`'s own text color) — the same disabled/active relationship those other two controls already express, applied consistently to the badge's numbers too.

## Z-index scale

| Token | Value | Use |
|---|---|---|
| `z-base` | 0 | Decorative backdrop, or the "back" layer in a local front/back pair |
| `z-raised` | 1 | Content sitting above its own local backdrop, or the "front" layer in that same pair |
| `z-sticky` | 5 | Sticky headers, pinned within their own scroll container |
| `z-overlay` | 10 | Floating controls on top of scrollable/hoverable content |

Introduced once the Tag Pool/Recommendations tab panel started keeping both bodies permanently mounted (one hidden via `display:none`, not unmounted — see "Tag Pool and Recommendations became two tabs" below). Before this, every `z-index` in the app (`KonomiApp`'s halftone-vs-content layering, `RecommendButton`'s star layers, `ResultCard`'s flip faces, `CollapsibleSection`'s sticky header, `ScrollFadeArea`'s and the carousel's hover arrows) was a standalone ad hoc number that happened never to collide only because nothing actually overlapped anything else spatially. A coexistence moment — like a tab switch, or a sticky header and scrolling content sharing the same screen position — is exactly the case that turns "lucky" into "broken," so the scale exists now rather than after the first real collision.

`z-base`/`z-raised` describe a *local* front/back relationship within one component's own stacking context (`RecommendButton`'s two star layers vs. its button; `ResultCard`'s active vs. inactive flip face) — they don't compete with `z-sticky`/`z-overlay` globally, just with each other, locally.

One documented exception: `ResultsHeader`'s Clear ✕ button uses `z-raised` to win a hit-test against a *sibling section* (the results carousel), not a local backdrop within its own component — see "Carousel click-through vs. touch-scroll-chaining" below for why. `z-raised`'s value (1) still only needs to beat the carousel's default, unset stacking (effectively 0) at that one overlapping point; it isn't competing with `z-sticky`/`z-overlay` there either, so the token's actual *value* still behaves as documented. Only its *scope* (local-only) is stretched, for one specific, confirmed-live reason — not a precedent for using `z-base`/`z-raised` to arbitrate between arbitrary unrelated sections generally.

**A plain `position: static` element always paints *behind* any sibling that has an explicit `position` + `z-index`, regardless of DOM order — even `z-index: 0`, or another element's merely-unset-but-positioned default, beats it.** Found when `MixerBar`'s own root (no `position`/`z-index` of its own) started rendering *behind* `ResultCard`'s front face once the bar's edit-mode content grew tall enough to visually overlap the results grid above it — `ResultCard`'s front face carries `position: absolute` + `z-raised` for its own local flip-face stacking (see above), which is enough to win against any plain static sibling it happens to overlap, even one that comes later in the DOM and reads, visually, like it should be "in front." The fix was giving `MixerBar`'s root its own explicit `relative z-overlay` (the same token it already uses for its page-level stacking — see "The single box that grows" below) rather than trying to lower `ResultCard`'s. General rule: any element that needs to reliably render on top of arbitrary page content needs its *own* explicit `position` + `z-index` — being later in the DOM is not sufficient once *any* sibling anywhere in the same stacking context has its own explicit stacking.

### Carousel click-through vs. touch-scroll-chaining — `pointer-events: none` isn't free

The results carousel's `ScrollFadeArea` wrappers (`root`/`scrollRef`/`contentRef`, in `RecommendationsBody.tsx`) carry real, invisible `pt/pb-[40px]` padding reserved for the card-flip's 3D bulge (`ResultCard`'s `rotateY`, measured live at up to ~33.5px/28.5px beyond the resting card box). Because every one of those wrappers just sizes itself to fit its content, all three share the *identical* bounding rect — 40px taller above and below the visible cards than the cards themselves. That inflated top band geometrically overlaps `ResultsHeader`'s Clear ✕ button by ~24px (confirmed live via `getBoundingClientRect` on both), which used to silently swallow clicks meant for Clear ✕ — fixed, originally, by giving all three wrappers `pointer-events: none` (`ScrollFadeArea`'s `disableWrapperPointerEvents` prop) so hit-testing fell through to whatever was actually there.

That fix had an unrelated side effect nobody had reason to check at the time: `pointer-events: none` doesn't just exclude an element from *click* hit-testing — on this device/engine, it also disqualifies it from native touch-scroll-gesture-*chaining* candidacy. `scrollRef` is this carousel's actual `overflow-x-auto` viewport — the element a horizontal swipe needs to reach once it's chained up from wherever it started (a card's cover, back, or tag area). With `scrollRef` set to `pointer-events: none`, a horizontal swipe starting on a card's tag area only reached the carousel when the tag area *itself* was an active/overflowing vertical scroll container — confirmed live, on a real device, that this was the actual discriminating variable, not tag-chip `draggable` (a competing theory, ruled out the same way) and not `overflow-y` on the tag area itself (a first fix attempt gated `overflow-y-auto` on `hasOverflow`, which was independently correct in isolation but addressed the wrong element entirely and was reverted rather than shipped as dead weight).

Splitting "the box tall enough to not clip the flip bulge" from "the box that must be `pointer-events: auto` for gesture-chaining" doesn't work as a pure CSS split: any element with `overflow-x: auto` is subject to the standard CSS Overflow rule that a non-`visible` value on one axis forces the other axis's *computed* value to `auto` too — so whichever element handles the real horizontal scrolling can't be shrunk smaller than the bulge-inclusive height without either re-clipping the flip or simply recreating the identical click-through overlap at a smaller scale. The two constraints (must-be-tall, must-not-overlap-Clear✕) land on the same box either way.

**The fix: resolve the click-through concern by paint order instead of by hit-test exclusion.** `ResultsHeader`'s Clear ✕ gets `relative z-[var(--z-raised)]` so it wins the hit-test at that overlap point regardless of DOM order — the overlap region is empty, unpainted padding on the carousel side, so this can't visually cover anything real. `disableWrapperPointerEvents` is removed from the carousel's `ScrollFadeArea` entirely, so `scrollRef`/`root`/`contentRef` return to default `pointer-events: auto` and the carousel can participate in native touch-scroll-chaining regardless of whether a given card's tag area happens to be overflowing. (`RecommendationsBody`'s own grid — a separate, `pointer-events-none` div for a different reason, see that file's comment — is untouched; only the three `ScrollFadeArea`-owned wrappers changed.)

The lesson for next time: `pointer-events: none` is not just a click-hit-testing tool here — treat it as a candidate suspect any time native touch-scroll-gesture-chaining breaks near a wrapper that has it, even if the wrapper was added for an entirely unrelated (and still valid) reason.

**Debugging method, not just this bug's answer:** diagnosing this took far longer than it should have because the *container* (the scroll viewport) and the *target* (the chips inside it) were investigated in the wrong order — a `draggable`-on-chips theory got built out and only ruled out afterward. For any trapped-gesture bug — a swipe/scroll that reaches some elements but not others — do this before writing any fix:
1. **Isolate container vs. target first, live on the device**: does the gesture fail only when it starts on a specific interactive child (button, chip, draggable element), or also when it starts on empty space inside the same container with nothing under the finger? Empty-space failure means the *container* is the suspect; failure only on the child means the *target element itself* is. This one test partitions the entire theory space before any code gets read.
2. **Then read the scroll container's own computed `pointer-events`, `overflow-x`/`overflow-y`, and `touch-action`** — not the target's, not a nearby wrapper's, the actual element with `overflow-x/y: auto|scroll` that the gesture needs to reach. All three properties can independently disqualify an element from gesture-chaining candidacy, and none of them announce themselves in a way a visual inspection catches.
Skipping straight to a plausible-sounding fix (as happened here, twice — the `hasOverflow` gate, then the `draggable` theory) burns iterations on a component that was never the trap. The empty-space test plus the computed-style read is cheap, mechanical, and conclusive — do it first.

## Runtime-computed dimensions: inline styles, never interpolated Tailwind classes

Tailwind's class scanner needs the *complete* arbitrary-value class to appear as static source text to generate CSS for it — a class built by interpolating a runtime value into a template literal (`` `max-h-[${n}px]` ``) is invisible to that scanner and silently produces no rule at all, not a build error, not a runtime warning. This has been hit three separate times now: `--result-card-height` (a shared CSS custom property was the fix, not a computed class — see "Recommendations layout" below), `TagPoolBody`'s `CHIP_AREA_HEIGHT` (a literal string constant, not a template literal), and `ScrollFadeArea`'s `heightPx` prop (an inline `style={{ maxHeight }}` override, not a computed class — see "MixerBar" below). **The rule: any dimension only known at runtime — measured, dragged, or otherwise computed from live state — gets an inline style, a CSS custom property, or, if it must be a Tailwind class, a value baked in as a literal string at build time. Never a class string built by interpolating a variable.** Reaching for a template-literal arbitrary-value class is the signal to stop and use one of the other three instead, before it becomes a fourth instance of this same bug.

## A custom class named `font-sans`/`font-serif`/`font-mono` loses to Tailwind's own utility of the same name

Tailwind v4 generates its three built-in font-family utilities (`font-sans`, `font-serif`, `font-mono`) into its `utilities` layer, and utility layer always wins over `@layer base` regardless of source order — a hand-written `@layer base { .font-mono { font-family: ... } }` override of one of these three specific names can never actually apply. **The fix: override the underlying `--font-mono`/`--font-sans`/`--font-serif` token in an `@theme` block instead, so Tailwind's own utility generates the right rule in the first place — never a same-named class in `base`.** Hit exactly this trap once already: `.font-mono`'s override silently lost the fight, and Space Mono never actually loaded (confirmed via `document.fonts` staying `"unloaded"` while `font-display`/`font-body` — unrelated names, no built-in Tailwind utility to collide with — loaded fine). Fixed by moving the override into `@theme { --font-mono: ...; }` in `globals.css`. Any future custom font-family class is safe as long as its name isn't one of those three reserved words.

## `line-clamp` clips descenders — it gives zero allowance for them

`-webkit-line-clamp` (Tailwind's `line-clamp-N`) clips at exactly `N × line-height`, full stop — it has no concept of a glyph's descender extending below that boundary. Any clamped text whose final line ends in a descender (`g`/`y`/`p`/`q`/`j`) will have it hard-clipped the moment `line-height` is tight relative to the font's actual metrics, regardless of anything else on the page — confirmed live in `TagSlot`'s filled-slot tag name (`leading-tight` = 1.05, clamped to 2 lines): a 2nd-line "g" clipped identically whether or not the caption below it ("TAP TO CLEAR") was even present, proving the clamp's own box is self-contained and doesn't know or care what sits below it.

**The fix is `padding-bottom` on the clamped element itself, not more `line-height`.** `overflow: hidden` (which `line-clamp` sets) clips at the element's *padding* box, not its content box, so a few px of bottom padding buys descenders real room without touching `line-height` or how many lines count as "the limit." `TagSlot` uses `pb-[4px]` — tested live at 2/3/4px; 4px was the first value where a real descender ("Cute Girls Doing **Cute Things**") rendered its full loop with no clipping. Reset to `pb-0` at any tier where the clamp itself resets to `line-clamp-none` (nothing to protect against once unclamped).

## Dashed borders: iOS WebKit clips them — accepted, not fixed

iOS WebKit drops the left/right segments of `border-dashed` on empty states (`TagSlot`'s empty tag slots, `RecommendationsBody`'s "MIX TAGS" placeholder) — not reproducible in desktop Chrome emulation, only confirmed live on-device. Investigated fully — outline-dashed also clips; SVG stroke-dasharray renders correctly but its continuous perimeter path slides/gaps at corners on resize. Accepted the cosmetic clip as the best trade (empty-states only, ~half of mobile traffic, no functional impact). Don't re-litigate.

## A visual gap has to match the other gap's *rendered* distance, not just reuse its token — and rotated ancestors make `getBoundingClientRect()` lie about that distance

Two independent instances now: `ResultsHeader.tsx`'s title row (`mb-[calc(var(--space-2xl)_-_7.08px)]`) and `Masthead.tsx`'s accent bar (`mt-[calc(var(--space-2xl)_-_9px)]`). Both hit the same shape of bug — a margin/gap reused the *same token* as a gap elsewhere on the page (space-2xl in both cases), on the reasoning that "same token = same gap," when what actually needs to match is the *rendered* distance between two visual edges, which isn't the same thing the moment anything else (invisible centering slack, a decorative element's own height) sits inside that margin alongside it. `ResultsHeader`'s title row is `items-center`-pinned to Clear ✕'s taller box, leaving ~7.08px of invisible slack above/below the title text itself; a flat `mb-2xl` there measured as a visibly bigger gap than the mixer's own plain 24px. `Masthead`'s accent bar sits *inside* the same margin as the "gap" — a flat `mt-2xl` before it made the real content-to-border distance `24 + 9` (the bar's own height), not 24, even though the bar itself sits flush against the true border with zero space after it. Both fixes are the same shape: `calc(var(--space-2xl) - Npx)`, where `N` is the real, measured, *already-documented* offset — margin + offset sums back to the token's own value, so the *visual* result matches the other edge instead of just the raw number.

**The generalized tell: before reusing a token as-is for "the same gap," check whether anything else occupies space inside that margin on either side being compared** — invisible alignment slack (a taller sibling forcing `items-center` slack), or a real, rendered element (a decorative bar, an icon's own padding) between the margin and the boundary it's supposed to reach. If something does, the flat token will only coincidentally look right, and only at whatever size happened to be checked.

**The trap that made `Masthead`'s instance harder to verify: a rotated ancestor (`rotate-[-0.5deg]`) inflates `getBoundingClientRect()`'s reported height for a wide child.** `getBoundingClientRect()` returns an axis-aligned box in *viewport* coordinates — for a child rotated along with its ancestor, a box significantly wider than it is tall gets measurably taller once its corners are computed post-rotation (a wide rectangle's rotated corners swing further vertically than a narrow one's). Confirmed live: the accent bar's own `height: 9px` (`box-sizing: border-box`, so 9px is genuinely its whole rendered box) measured as `14.65px` via `getBoundingClientRect()` — enough to make a real ~9px shortfall (`mt-2xl` alone, before the fix above) read as an already-flush ~0px gap when checked that way, the opposite of what was actually happening. The fix isn't a different measurement trick — it's not trusting `getBoundingClientRect()` at all for anything inside a rotated element, and reading the computed CSS box-model values (`height`, `border-width`, `margin`) directly instead. `ResultsHeader` isn't rotated, so its own 7.08px was safe to confirm via `getBoundingClientRect()` directly — this trap is specific to `Masthead` (currently the only rotated container in the app) and any future one.

## What's intentionally *not* tokenized

A few categories of number show up in components but aren't part of the scale above — they're one-off implementation details, not reusable design values, so folding them into `tokens.ts` would just be noise:

- **Component-specific layout dimensions** — cover art height (114px), mixer slot height (92px), icon button size (30px), grid column minimum (208px), flex-basis breakpoints (250px/280px/460px), etc. These describe *one component's* geometry, not a shared scale. (`ResultCard`'s own overall height (`--result-card-height`) is the clearest exception — a real token specifically because a second component, the Recommendations empty-state placeholder, must always match it exactly. `--masthead-height`/`--header-row-height`/`--mixer-bar-height` are tokens for a related but different reason: not because another component must match them, but because `--result-card-height`'s own clamp formula needs each of them as an input — see "Recommendations layout" below for all four together.)
- **Decorative one-offs** — the two halftone dot patterns (9px tile on the page background, 8px tile on card covers — intentionally different, matching the original design), the starburst clip-path and its two circle sizes, badge/tilt rotation angles, theme-swatch gradient (necessarily inline — see below).

## Known intentional deviation

`TagScrollArea`'s scroll arrows (▲/▼) use `text-[8px]`, which is below the smallest defined type step (`2xs` = 10px) — and stays that way deliberately. These are functional scroll-control glyphs inside an 18×16px button, not typographic content, so they don't need to track the type scale the way body/label text does. Documented in a code comment at the call site.

## One documented exception

`ThemeSwitcher`'s theme-preview swatches use an inline `style` (not a token/Tailwind class) for their gradient background, because each swatch must render a *specific* palette's raw colors regardless of which theme is currently active — something CSS custom properties can't express (they only resolve to the active theme) and Tailwind can't express either (the gradient stops are dynamic per-palette data, not enumerable as static classes). This is called out in a code comment at the call site.

### `ThemeSwitcher`'s hover subtext replaces the native `title` tooltip

Hovering (or focusing) a swatch shows a custom line below the whole swatch group — `"Konomi ❀"` / `"Tide ࿐"` / `"Newsprint ░"` — instead of the browser's own `title`-attribute tooltip, which is why `title` was removed in favor of `aria-label` (kept for a11y, but it doesn't render its own visible tooltip). React state (`useState<ThemeKey | null>`), not CSS-only `:hover`, because three *different* strings need to render depending on which specific swatch is hovered — simpler than the `:has()`-based sibling-selector approach that would take to express the same thing in pure CSS. The subtext itself follows the same out-of-flow hint pattern used for `LevelSelector`/`TagPool`'s hints elsewhere in this file: `absolute top-full`, so it costs no layout space while hidden, with only `opacity` (not `display`/mount) toggling — confirmed live that it lands in the empty space to the right of the masthead's tagline with no overlap, so no extra clearance was needed here unlike those other hints. The decorative glyph per theme is a one-off UI pairing for this interaction specifically, not a design token (see "decorative one-offs" above).

### `LevelSelector` adopted the same hover-subtext pattern, replacing its own `title` tooltips

Same mechanic as `ThemeSwitcher` above (per-segment `useState`, `aria-label` instead of `title`, `absolute top-full` line below the whole segmented control, opacity-only toggle) — this replaced the per-segment native `title` tooltip approach `LevelSelector` had been using, which itself had replaced an earlier single shared hint line for just the active option (see `tagPool.ts`'s `LEVEL_OPTIONS.hint` strings for the current text/glyph per option). One real difference from `ThemeSwitcher`'s version: `LevelSelector`'s segmented control carries `shadow-[var(--elev-2)]` (a hard 3px-offset shadow), so the subtext's clearance needed `mt-[var(--space-sm)]` (6px), not the `mt-[var(--space-xs)]` (4px) `ThemeSwitcher` uses — at 4px, only ~1px of actual clear space existed past the shadow's 3px drop, and the subtext visually blended into it. `ThemeSwitcher`'s swatches don't carry a shadow that deep, so `mt-xs` never had this problem there.

`MatchSelector` (Mixer's MIN TAG MATCH control) is now a third instance of this exact pattern — same `useState`/`aria-label`/`mt-sm` treatment as `LevelSelector` (it shares the same `elev-2` shadow), with its own hint strings (`"match 1+ tag"` / `"match 2+ tags"` / `"match all 3 tags"`). See the Mixer section below for its hint copy and placement.

### `ResultCard`'s lock/swap icon hints are the same idea, but three real differences from every version above

`ResultCard`'s lock and dice (swap) icons show a hint chip — `"lock"`/`"unlock"` for the lock icon, `"swap"`/`ERROR_MESSAGE["impossible-min"]`/`"no swaps available for this mix"` for the dice icon depending on *why* it's disabled. One `useState<"lock" | "swap" | null>` tracks which icon is hovered/focused, and a single hint chip renders whichever is active — same shape as the other three instances.

**Only the `impossible-min` branch reuses `RecommendButton.ERROR_MESSAGE` (now exported); the `!canSwap` branch does not reuse `ERROR_MESSAGE["no-match"]`, despite an earlier version of this component doing exactly that.** `canSwap` (in `useKonomi.ts`) and recommend's `no-match` error check different things: `canSwap` excludes every currently-*shown* title (locked and unlocked) and asks whether anything else in the catalog qualifies, while `no-match` excludes only *locked* titles when scoring the whole catalog. They're not the same condition — `canSwap` can be `false` while a fresh RECOMMEND would succeed fine (e.g. every series matching this mix happens to already be displayed and none are locked; recommend's pool isn't empty, since it doesn't exclude the shown-but-unlocked ones). Reusing `"no series match this mix"` for `!canSwap` was therefore inaccurate in that case — it claims nothing matches when several series do, they're just already on screen.

**The copy went through one more correction: `"all series shown for this mix"` (an intermediate version) was itself replaced with `"no swaps available for this mix"`,** because it asserted something not always true — that the currently-shown cards belong to *the current mix*. Results can go stale: tags can change after the last RECOMMEND without a fresh one being triggered (see "Locked cards are real, positioned members of `results`" and the mixer error system notes below on why there's no live filtering), so what's on screen may reflect an older tag selection than the one `canSwap` is currently being evaluated against. `"no swaps available for this mix"` only claims what `canSwap` actually reports — no series is available to swap in — without asserting anything about whether the shown cards themselves still match the current mix, so it holds in both the fresh-results and stale-results cases.

Three more things are genuinely different here, all forced by this component's context (a photo-backed card in a grid that can be as narrow as 208px), not arbitrary variation:

1. **In-flow, not `absolute`, and positioned beside the icons, not below them.** The icon row is a `flex items-center` row; the hint is a normal third flex item after the two buttons (not `position: absolute` + `top-full`), so it sits to their right at the same vertical center. This was a deliberate design choice (explored live, tried below-the-icons first) — not a technical requirement the way `LevelSelector`'s wrap-clearance fix was.
2. **Conditionally mounted (`{activeHint && <span>...}`), not always-rendered with an opacity toggle.** Because the hint is now in-flow, an always-present-but-invisible chip would permanently reserve its padding/border footprint next to the icons even while hidden — the exact failure mode the other three instances avoid by staying `absolute` (out of flow) instead. Mounting only when there's a hint to show keeps the icon row exactly as wide as its two 30px buttons the rest of the time.
3. **An opaque bordered/shadowed chip (matching `ICON_BTN`'s own `elev-1` treatment), not plain muted text.** Every other hint in this app floats over a flat `surface`/`bg` color; this one floats over arbitrary AniList cover art, so it needs its own background to stay legible regardless of the photo underneath.

**Wrapping, not `whitespace-nowrap`.** Every other hint in this app fits on one line at the widths it appears at; this is the first one that can't — `"no series match this mix"` routinely can't fit unwrapped in a 208px-wide card. The chip uses `min-w-0` (not the flex default `min-width: auto`, which would refuse to shrink below the content's unwrapped width and overflow the card instead) so it wraps within whatever space is left in the row after the two icon buttons. Confirmed live at the grid's narrowest column width that the longest hint wraps to two lines and stays inside the card.

### The icon buttons themselves must never resize or reposition when the hint mounts

Two bugs surfaced live after the hint chip shipped as an in-flow third sibling, both because the icon row is a normal flex row and the two 30px buttons were never told to opt out of flex's default behavior:

1. **The buttons could shrink.** `w-[30px] h-[30px]` sets a button's preferred size, but every flex item still defaults to `flex-shrink: 1` regardless of an explicit width — so when the hint chip mounted and the row's total content briefly exceeded available space, the *buttons* could shrink instead of the hint (which has its own `min-w-0` specifically so it, not the buttons, absorbs any overflow by wrapping). A shrinking button moves out from under the cursor mid-hover if the pointer isn't dead-center, which fires `mouseleave` → hides the hint → button springs back to full size → `mouseenter` fires again — a flicker loop, confirmed as the actual mechanism behind a "hard to trigger the hint" report. Fixed with `flex-none` on `ICON_BTN`, which fixes both `flex-grow` and `flex-shrink` at once (stronger than just `shrink-0`, though either would have worked here).
2. **The buttons could shift vertically when the hint wrapped.** The row uses `items-center`, which centers all children against the *tallest* item's height — normally the 30px buttons themselves, so nothing moves. But once a long hint wraps to two lines, the hint chip becomes taller than 30px, and `items-center` recenters the whole row against that new taller height, nudging both buttons up or down. The fix has to be conditional, not a single static alignment, because a single-line hint centering against the icons still looks better than top-aligning it (confirmed live, compared side by side) — so `items-center` is right whenever the hint fits on one line, and only `items-start` once it wraps. CSS has no selector for "did this text wrap," so `hintWrapped` is measured directly: a `useLayoutEffect` (not `useEffect` — this needs to read layout and write alignment-affecting state before the browser paints, or there'd be a one-frame flash of the wrong alignment right when the whole point is avoiding visible jumps) computes the hint span's expected single-line height from its own computed `line-height`/padding/border — not a guessed pixel constant, so it stays correct across font-size or theme changes — and compares it to the actual rendered `offsetHeight`. Taller means it wrapped, and the row's alignment class switches accordingly. Confirmed live via exact `getBoundingClientRect()` comparisons that both icons hold pixel-identical position across all three states: no hover, a single-line hint, and a wrapped two-line hint.

**The dice (swap) button uses `aria-disabled`, not the native `disabled` attribute, for the first time in this app.** A truly disabled button can silently fail to fire hover/focus events in some browsers — which would break exactly the feature this button needs (explaining *why* it's disabled). `aria-disabled` plus an early-return guard in the `onClick` handler preserves the "can't actually swap right now" behavior while keeping hover/focus reliable regardless of disabled state.

**Swap shows no hint at all while the card is locked**, rather than a fourth message explaining that locking blocks swapping — the lock icon's own hint (`"unlock"`) already communicates that, and a second, differently-worded explanation on the adjacent icon felt redundant rather than clarifying. This was an assumption made without an explicit spec for the locked case (the request only described the three unlocked states); worth revisiting if it doesn't read as intended.

## Tag Pool hierarchy

The Tag Pool section (`TagPoolBody.tsx`) groups its ~280 tags/genres into 5 top-level sections (Genres, Theme, Setting, Characters, Demographic — "Characters" is a display-only rename of what's still keyed/categorized as `cast`/`Cast-*` throughout the code). Only Theme further splits into labeled subsections (Action, Fantasy, Sci-Fi, etc.) — Setting and Characters merge their categories into one flat list each (same tags, no subsection grouping shown), and Genres/Demographic were always flat. The hierarchy itself (which AniList categories merge where) is static config in `src/lib/konomi/tagPool.ts` — not duplicated in the component.

**Subsection labels** (e.g. "Action", "Sci-Fi" within Theme) reuse Mixer's existing small-caption style (`font-mono text-[length:var(--text-2xs)] tracking-[var(--tracking-xl)] text-[var(--muted)] uppercase`) rather than introducing a new label treatment. They scroll inline as plain labels within whichever section is active — not sticky, not a second nav level.

**Genres are tags**: genres (from `series.genres`) are represented as `TagInfo` objects (`isGenre: true`, `category: null`, `avgRank: 100`) merged into the same `allTags` array as real tags, computed in `getCatalog()`. `avgRank: 100` is a deliberate ceiling — genres always clear any rank-threshold filter, since a genre match is at least as strong a signal as any single tag. This means genre chips need zero special-casing anywhere downstream: they render via the same `TagChip`, drag into the same mixer slots, get randomly picked by "Random ×3", and are scored by `scoreSeries` (which checks `series.tags` *or* `series.genres` — the only change genres required in `scoring.ts`). Result cards (`ResultCard.tsx`) merge a series' tags and genres into one chip list sorted by `avgRank` (via a `name → avgRank` lookup built once in `useKonomi.ts`), so genres float to the top and display identically to tags there too.

### Section navigation is a horizontal tab strip, not collapsible sections

`CollapsibleSection.tsx` — the per-section expand/collapse component, its `localStorage`-backed expand state, and the sticky-header/mask machinery built to keep those headers visually transparent while scrolling (see the git history for that whole saga) — is **deleted entirely**, not kept around in reduced form. The 5 sections are now tabs (`SectionTabStrip.tsx`), rendered in a horizontal strip above the chip area; only the active section's tags render below it at all. There's no expand/collapse state left anywhere in the Tag Pool, and therefore no sticky-header-vs-scrolling-content interaction to solve in the first place — the entire class of bug that machinery existed for doesn't exist anymore.

**Tab styling deliberately reuses the old collapsible-header's exact type treatment** (`font-display text-[length:var(--text-lg)] uppercase tracking-[var(--tracking-sm)]`) rather than introducing a new one — active tab `text-[var(--ink)]`, inactive `text-[var(--muted)]`. This is one step smaller than `MixerBar`'s own `text-xl` title row above it (inside the pool panel — see "MixerBar" below), on purpose: the two rows read as a hierarchy (the bar's own Mixer/Edit Tags title, then a section toggle nested inside the pool panel specifically), not as one flattened row of equal-weight controls. Tabs are separated by a plain, decorative `/` (`aria-hidden`, never counted as a tab). (This section tab strip previously sat below `PanelToggleHeader`'s own Recommendations/Tag Pool toggle, which used the same divider style one level up — that toggle is retired; see "MixerBar" below for what replaced it.)

**Real `tablist`/`tab`/`tabpanel` semantics, roving tabindex, automatic-activation arrow keys.** Each tab is a `<button role="tab">` with `aria-selected`, `id`/`aria-controls` linking it to the single `role="tabpanel"` div below (`tagpool-tab-<key>` / `tagpool-panel-<key>`). Roving tabindex: only the active tab has `tabIndex={0}`; every other tab is `tabIndex={-1}`, standard practice so `Tab` moves focus in and out of the whole strip in one stop rather than tabbing through every section individually. Arrow-key navigation uses "automatic activation" — `ArrowLeft`/`ArrowRight` (wrapping at both ends) and `Home`/`End` immediately switch the active section *and* move focus together, rather than moving focus alone and waiting for a separate activation key. This matches how OS-level tab strips typically behave and is simpler to reason about than tracking focus and selection as two independent pieces of state.

**The selected-count badge** (`Theme 2`, shown only when count > 0) moved from the old header's `title ▾` cluster onto the tab label directly — same counting logic (`tagsForSection()`, counts across the whole section including all of Theme's subsections combined, not per-subsection), just no trailing chevron anymore, since there's nothing left to expand/collapse.

**Auto-scroll the active tab into view** via a plain `element.scrollIntoView({ inline: "nearest", block: "nearest" })` call on the active tab's own button ref, in an effect keyed on the active section. This needs no handle into `ScrollFadeArea`'s internal scroll element at all — `scrollIntoView` walks up to the nearest scrollable ancestor on its own, which is exactly the tab strip's own viewport. `block: "nearest"` keeps this from ever scrolling the page vertically as a side effect.

**State persistence is mostly free, with one new edge case collapsible sections never had.** `activeSectionKey` is plain `useState` inside `TagPoolBody`, which never unmounts while browse mode is active (`MixerBar` only toggles a `max-h-0 overflow-hidden` class on its pool panel — see "MixerBar" below) — so the active section and the tab strip's own scroll position both survive closing and reopening edit mode for free, the same mechanism documented there for the pool panel as a whole. The new edge case: changing **Level** can make the currently-active section disappear entirely (e.g. everything but Genres is empty at Level 1 "Casual") — collapsible sections never had to handle this, since a hidden section just stayed collapsed-and-invisible in place. The fallback (first still-visible section, always Genres) is computed as a plain derived value at render time (`visibleSections.find(...) ?? visibleSections[0]`), *not* written back into state via `setActiveSectionKey` inside a `useEffect` — that would be the exact `react-hooks/set-state-in-effect` anti-pattern this codebase already avoids elsewhere (see `tagPoolPrefs.ts`'s own history). Leaving the stored key untouched while its section is merely hidden also means raising the level back up resumes showing whatever was actually active before, instead of having permanently reset to Genres the moment it first disappeared.

**Switching section tabs resets the chip area's scroll to the top**, by giving the chip `ScrollFadeArea` a `key={activeSectionKey}` — changing the key forces a clean remount (and therefore a fresh `scrollTop`) on every section switch. Per-section scroll memory (resume exactly where you left off in *each* section, not just the currently-active one) was considered and explicitly declined for now — reset-to-top is a fine default, and remembering N independent scroll positions isn't worth the complexity it'd add.

### The chip area hugs short sections and only caps for long ones — a real bug surfaced getting there

The chip area uses `max-h-[50dvh]` (`CHIP_AREA_HEIGHT` in `TagPoolBody.tsx`) — a **cap**, not a fixed height. A short section (Genres, Setting, Demographic) hugs its own content; a long one (Theme) caps at the ceiling and scrolls past it. `CHIP_AREA_HEIGHT` used to be pegged to `--result-card-height` (`max-h-[calc(var(--result-card-height)-42px)]`), back when Tag Pool was a full-page tab sharing a panel with Recommendations and the two needed comparable heights — that peg no longer means anything now that this component lives inside `MixerBar`'s own pool panel instead (see "MixerBar" below), so it caps against the viewport directly. `dvh`, not `vh`: `dvh` avoids the well-known mobile Safari/Chrome dynamic-toolbar jump plain `vh` produces — a real concern here regardless of whether the bar sits at a fixed or normal-flow position, since this cap engages while the pool panel is open and visually anchored near the bottom of the screen either way. Either way, this has to be a literal string, not built via template interpolation — see "Runtime-computed dimensions" above, which this exact constant is one of the three cases motivating that rule.

**On desktop, this default can be overridden by a live pixel value instead** — `MixerBar`'s drag-resize handle (see "MixerBar" below) passes a `chipAreaHeightPx` prop through to `ScrollFadeArea`'s `heightPx`, an inline `style={{ height }}` override that takes priority over the `max-h-[50dvh]` class entirely when present. Fixed, not capped, to match: this area must never hug/shrink to fit whichever section is active — see "MixerBar" below for why the panel's total size is now exact rather than content-driven, and a real CSS gotcha (`overflow:hidden` clipping a shorter-than-content flex column from the *start*, not the end) that surfaced building it. `TagPoolBody` itself needed no other changes to support this — `heightPx` is `undefined` only pre-hydration.

**A real, non-obvious bug surfaced while fixing the chip shadow-clipping problem this same change introduced.** Base-size `TagChip` carries `shadow-[var(--elev-2)]` (3px 3px 0, bottom-right, no blur); `ScrollFadeArea`'s vertical viewport sets `overflow-y-auto`/`overflow-x-hidden`, so a chip's shadow bleeding past the content's own bottom/right edge gets clipped there — same root cause as the results carousel's shadow-clipping bug (see below). The carousel's fix (pad the content, then cancel the added size with a matching negative margin so nothing downstream shifts) was tried here first and looked right in isolation — but it created a *different*, previously-unseen bug: it made short sections show a scrollbar/fade/arrows that shouldn't have been there at all. Root cause: `element.scrollHeight` does not shrink back down to match a compensating negative margin the way normal `height: auto` layout does — the padded-then-canceled wrapper's `clientHeight` correctly came out unchanged, but its `scrollHeight` still measured a few px taller, which is exactly what `ScrollFadeArea`'s `hasOverflow` check (`scrollHeight > clientHeight + 1`) compares. Confirmed live: a short, otherwise non-scrolling section spuriously showed a bottom fade and a down arrow. Since this area now hugs rather than holding a fixed height, there's no exact-footprint invariant to protect here the way the carousel has — so the actual fix is simpler: just let the box legitimately grow by 3px to fit the shadow, **uncanceled** (`pb-[3px] pr-[3px]`, no negative margin). This is the same shape of fix `CollapsibleSection`'s own history used for this identical problem (a plain `last:mb-[var(--space-md)]`, never canceled) — accepting a few px of real, harmless size increase instead of trying to erase it turned out to be the correct call both times.

### `ScrollFadeArea` — shared scroll/fade mechanic, now with a real horizontal orientation

`TagScrollArea` (per-card tags), the Tag Pool's chip area, `SectionTabStrip`, and the results carousel (`RecommendationsBody`) all share one mechanic: a bounded viewport, edge gradient fades that appear only when content is actually scrollable in that direction, hover-revealed arrow buttons with press-and-hold continuous scroll, and (for the two horizontal callers) native trackpad/touch scrolling plus an explicit wheel-to-scroll translation. That's `ScrollFadeArea.tsx` — `orientation?: "vertical" | "horizontal"` (default vertical, so the two original vertical callers are untouched), everything else generalized to whichever axis is the main one.

**This was a real consolidation, not just a rename.** The results carousel used to be a fully bespoke implementation, specifically because `ScrollFadeArea` was vertical-only at the time (see the carousel's own git history) — once horizontal support existed for the tab strip anyway, the carousel's mechanics turned out to generalize cleanly too, via a small set of caller-tunable props rather than one-off special cases:

- **`getScrollStep?: () => number`** overrides the fixed `scrollStep` number for a plain click, for the one caller whose "one unit" isn't constant — the carousel's card width steps through 4 responsive tiers, so it's measured live off the actual rendered DOM (`card.getBoundingClientRect().width + gap`) rather than hardcoded.
- **`scrollResetKey?: unknown`** scrolls the viewport back to its start edge (instantly) whenever this value changes — generalizes the carousel's own "`recommendGen` bumped, scroll back to card 0" `useEffect` into a plain prop (`scrollResetKey={recommendGen}`) instead of a caller-owned ref + effect.
- **`arrowWidth`/`arrowHeight`/`arrowShadow`/`arrowInset`** parameterize the arrow buttons' geometry — every existing caller keeps `ScrollFadeArea`'s own small (18×16), flat, flush defaults; the carousel is the one caller that needs bigger (36×36), shadowed, edge-inset (`var(--space-md)`) arrows, since they sit over arbitrary cover art rather than a flat surface color.
- **`scrollPaddingStart?: number | string`** (renamed from `scrollPaddingTop`, since it now applies to whichever axis is the main one — top for vertical, left for horizontal) accepts a CSS length string, not just a px number, so the carousel's own `6%`-of-the-row peek still works unchanged.
- **`arrowVerticalOffsetPx?: number`** (horizontal-only, default `0`) nudges the arrows' cross-axis centering by a caller-supplied px amount, added for `MixerBar`'s filters row: that row's `ScrollFadeArea` wrapper carries real, asymmetric bottom padding (room for `LevelSelector`'s own hover-subtext/shadow-bleed, canceled back to zero *visually* via a negative margin on an *ancestor*, not on `ScrollFadeArea`'s own root) — so the default 50% centers on the padded box, not the visibly obvious control row inside it, reading as bottom-aligned instead of centered. Confirmed live as a real bug before the fix (arrow measurably off-center against the actual buttons) and after (byte-identical center once `arrowVerticalOffsetPx={-13}`, half the 26px pb, was applied). Every other horizontal caller has no such asymmetry and passes nothing, seeing no change.

**What genuinely doesn't transfer, and stays a caller concern rather than a `ScrollFadeArea` prop:** the carousel's row is a plain CSS `grid` above 1152px and only becomes a scroll container *below* that breakpoint — `ScrollFadeArea`'s own viewport is always scrollable, with no concept of "static grid above N px," so that breakpoint switch lives in `RecommendationsBody`'s own row markup (`grid ... max-[1152px]:flex max-[1152px]:flex-nowrap`), passed to `ScrollFadeArea` as `children`. Confirmed live this doesn't create a false-positive overflow signal in grid mode, even though `ScrollFadeArea`'s own viewport is *unconditionally* `overflow-x-auto` now (not gated to the carousel breakpoint the old bespoke version was): a CSS grid container's own padding doesn't expand its rendered outer width past its box the way a block/flex wrapper's does — its `1fr` columns just adapt to whatever's left inside the padded content box — so `pr-[5px]`/`pb-[5px]` (the same shadow-clipping fix described below) never trips `hasOverflow` in grid mode, only in the genuinely-overflowing carousel mode where it was already true regardless.

**`height` is vertical-only** — for `orientation="horizontal"`, the viewport always takes `w-full` instead, since both horizontal callers want the full width available to them and neither needs a per-instance sizing prop. **`snap`** now toggles `snap-x`/`snap-y` depending on orientation (only the carousel and `TagScrollArea` currently use it, plus `SectionTabStrip` for `snap-x`).

**No `onWheel` handler, on either horizontal caller — reverted, not an oversight.** A version of this component once summed `e.deltaX + e.deltaY` into `scrollRef.scrollBy({ left })`, specifically so a plain vertical-only mouse wheel could still drive horizontal scroll (a genuine trackpad two-finger horizontal swipe already reports real `deltaX` and scrolls a horizontally-overflowing container natively, no JS needed — only a wheel with *no* horizontal capability at all needed help). That fix caused a real, reported regression: a genuine *vertical* scroll gesture — mouse wheel, trackpad, or a mobile scroll — got hijacked into horizontal row movement the instant the pointer happened to be over a horizontal `ScrollFadeArea` (the results carousel, or a card's `TagScrollArea` nested inside it), interfering with scrolling the page itself. Removed entirely: native browser behavior already handles the case this was trying to help (real horizontal input scrolls the row on its own), and it never cross-translates a vertical gesture into horizontal movement the way the custom handler did. Confirmed live post-removal: a vertical wheel/scroll over the results row scrolls the *page*, not the row; a horizontal wheel/trackpad gesture over the same row still scrolls it correctly, snap-mandatory and all; the arrow buttons are unaffected either way (they never went through `onWheel`). The one accepted tradeoff: a mouse with *no* horizontal scroll capability at all can no longer wheel-scroll these rows — arrow buttons (always present, unaffected) are the fallback for that input type now, same as they always were for anyone without a trackpad/wheel at all.

**Removed entirely, not kept in reduced form:** `topInset`, `topMaskSize`, `topMaskFlatSize`, `stickyOverlay`, `onScrollContainerMount` — all of it existed solely for the old Tag Pool sticky-header mask system (see the section above), and nothing else in the app ever used them.

One implementation detail that still matters: `ScrollFadeArea` observes an **inner, intrinsically-sized content `div`** with `ResizeObserver`, not the bounded scroll viewport itself. A fixed/full-size viewport's own box never changes size on its own, so a `ResizeObserver` on it would never fire from content changes alone. The inner div has no fixed size, so its rendered extent (height for vertical, width for horizontal) directly tracks its children — which `ResizeObserver` does report.

### `TagScrollArea` gets the carousel's vertical-scroll treatment; the Tag Pool's chip area deliberately doesn't

Same underlying ideas as the results carousel (peek + snap + arrow affordance), applied to `TagScrollArea`'s vertical chip rows instead of horizontal cards — and *not* applied to the Tag Pool, on purpose.

**Why `TagScrollArea` can snap and the Tag Pool's chip area can't.** Chips wrap into fixed-height rows (33px: 27px chip + 6px `--space-sm` gap), so there's a real uniform unit to snap to. The Tag Pool's active section can still mix chip rows with sub-labels of varying group sizes (Theme's 10 subsections, each a different length) — no consistent unit to snap to that wouldn't feel arbitrary. So: `TagScrollArea` passes `snap` to `ScrollFadeArea`; the Tag Pool's chip area doesn't.

**Snap points come from the chips, not from a row wrapper element** — there isn't one; chips wrap via plain `flex flex-wrap`, so there's no per-row DOM node to hang `scroll-snap-align` on. `scroll-snap-align: start` is instead applied via a descendant selector, `[&_button]:snap-start`, on `TagScrollArea`'s own chip-wrapping div — not baked into `TagChip.tsx` itself, which is also used un-snapped in the Tag Pool and shouldn't need to know about scroll-snap at all. This works because every chip in the same row shares that row's exact Y position (confirmed live via unrounded `getBoundingClientRect()`), so N snap-aligned chips in one row collapse to one effective snap point — not N competing ones.

**Both a "next row" and a "previous row" peek**, mirroring the carousel's two-sided peek. `TOP_RESERVE_PX` (14) is passed as `scrollPaddingStart` — the same `scroll-padding-left` trick the carousel uses, just the vertical axis: a `snap-start` row settles 14px in from the true top instead of flush against it (6px of that is the row-to-row gap itself, empty space; the remaining 8px is the actual visible previous-row peek in the steady/mid-list state). `TAG_AREA_HEIGHT` is `121px` — not a value that gives an identical peek in every scroll position, which turns out to be impossible with this mechanism (see below), but a deliberate compromise landed on after two earlier attempts:

- A bottom-peek regression first showed up when `scrollPaddingStart` was added without growing the viewport to compensate: everything shifted down 14px, squeezing the previously-working ~13px bottom peek entirely off the edge (confirmed live via row-Y measurement: rows landing 1px past the box edge, zero visible). The first fix attempt, `126px` (assumed a symmetric 14px peek both sides), was subtly wrong — the original bottom peek was actually 13px, not 14px — and let the whole 4th row fit instead of peeking. Correcting to account for the real 13px restored it (confirmed via `scrollTo({top: 33})` settling at `19`, with the next row peeking exactly 13px).
- Even at 126px, the very first row (index 0) showed all 4 rows fully, no peek at all — proven mathematically, not just observed: reaching the "ideal" row-0 scroll position wants `scrollTop = 0 − TOP_RESERVE_PX` (negative), which the browser clamps to `0`, so row 0's reservation goes unused — and that unused 14px doesn't vanish, it becomes 14px of *extra* room at the bottom instead. That means the bottom peek at row 0 is mathematically always exactly `TOP_RESERVE_PX` bigger than the peek anywhere else in the list, for *any* single fixed height — there is no height where both cases match. A real `padding-top: 14px` on the chip-wrapping content div was tried to force row 0 to consume its reservation like every other row — confirmed live that it does fix the peek-size math, but at the cost of a genuine regression: a permanently empty 14px gap between the card's meta text and the first chip row, visible even before there's anything to peek at (flagged directly: "there is a weird unexpected space below the title"). Reverted.
- Final call: pick one height that keeps *both* states showing a genuinely partial (non-zero, non-full) peek, rather than eliminating the size mismatch outright. `121px` gives an 8px peek at every position after row 0 (matching the top peek's own 8px) and a 22px peek at row 0 specifically — bigger, but still visibly short of a full 27px row. Confirmed live via direct row-Y measurement in both states.

**Growing `TagScrollArea`'s height has a required side effect**: `ResultCard`'s overall height and this inner area aren't independently sized (the card is a fixed box, not auto-height), so `--result-card-height` (`globals.css`) has to grow by the same total amount to keep the card's fixed height matching its actual content — and since the empty-state placeholder reads from that same token, it moves in lockstep automatically, with no separate edit needed there. Current value: `445px` (`421px` original + `24px`, the total `TAG_AREA_HEIGHT` grew across this whole sequence, settling at 121px).

**The top/bottom fade gradient shrank from 18px to 4px** (`fadeSize={4}`, new prop; `ScrollFadeArea`'s own default is still 18px). Confirmed live that the full-size gradient was fading out exactly the row it was supposed to preview — actively working against the peek instead of reinforcing it, once the peek itself became the primary "there's more" signal. Not removed to 0 outright: a small amount still reads as a depth cue at the edge, just no longer doing the signaling work the peek already does. **The Tag Pool was then also switched to `fadeSize={4}`**, even though it has no peek and didn't have the same functional problem — it just looked better once the two scroll areas were compared side by side, so this one's purely a visual-consistency call, not a fix for anything broken there.

**A click moves by exactly `VISIBLE_ROWS` (3) rows — `scrollStep={VISIBLE_ROWS * ROW_STEP_PX}` (99), not the viewport's own pixel height.** An early version tried `scrollStep = TAG_AREA_HEIGHT_PX` (the raw viewport height) on the theory that `snap-mandatory` would correct any imprecision to the nearest row regardless — but that reliably landed on the *wrong* neighboring snap point: snap points sit at an irregular `33k − 14` sequence (thanks to `scrollPaddingStart`), and the viewport height happened to round closer to the point 4 rows ahead than 3 rows ahead, so a click consistently overshot by one row. Deriving `scrollStep` directly from "3 rows over" — the actual quantity being asked for ("the row that was peeking becomes the new fully-visible one") — sidesteps the rounding question entirely instead of relying on snap to paper over it. Confirmed live in both directions, including from the very bottom of a short card, where a single click up correctly recognized less than a full "page" remained above and landed exactly at the top.

**Continuous-scroll speed is a per-caller prop (`continuousScrollSpeed`), not the single shared constant it started as.** The Tag Pool's continuous scroll (6px/frame) felt right; the exact same rate felt roughly 4x too fast on `TagScrollArea`. But tuning this rate down (6 → 1.5 → 0.25) kept feeling like it made no difference — because of a real, separate bug: with `scroll-snap-type: mandatory` active, the browser treats even a sub-pixel `scrollBy` nudge as a completed scroll gesture and immediately snap-corrects to the next full row, so *every frame* of the intended slow continuous scroll was actually a full snap-jump, completely dominating whatever rate was configured (confirmed via an isolated A/B: 20 ticks of `scrollBy({top: 0.25})` moved `104px` with snap active vs. `0px` with it disabled). Fixed in `ScrollFadeArea` by toggling `scrollSnapType` to `"none"` (inline style) for the duration of a hold, restoring it (`""`, letting the `snap-y snap-mandatory` classes take back over) the moment the hold ends — so the final released position still snaps correctly, but the hold itself moves smoothly frame-by-frame instead of snap-jumping.

That fix then exposed a second, previously-masked bug: with the snap-jump gone, `TagScrollArea`'s rate (0.25px/frame) produced *no visible motion at all* — `scrollBy` silently rounds a sub-1px delta down to `0` rather than fractionally accumulating it, so 0.25px/frame was never actually moving the element on its own; the snap-jump had been the only thing producing visible motion the whole time. Fixed with a fractional accumulator in `startContinuousScroll`'s `rAF` loop (`scrollRemainder` ref): each frame adds `continuousScrollSpeed` to the remainder and only calls `scrollBy` once the accumulated whole-pixel part is nonzero, so any rate — including well under 1px/frame — still scrolls at its correct average speed. With real motion finally decoupled from the snap-jump artifact, the actual felt-right rate turned out to be much higher than 0.25 — retuned live in several passes (0.25 → 0.375 → 0.9375 → 1.25 → 1.5) to the final `continuousScrollSpeed={1.5}`. The Tag Pool keeps `ScrollFadeArea`'s own default (6) without needing to pass anything — it was never affected by either bug, since it doesn't use `snap` at all.

### Long-press-to-continuously-scroll, added to `ScrollFadeArea`'s arrows — and two real bugs found building it

All four current `ScrollFadeArea` callers (`TagScrollArea`, the Tag Pool's chip area, `SectionTabStrip`, and the results carousel) get this for free, since they share the mechanism. A normal click still steps by `scrollStep` (or `getScrollStep()` for the carousel — see above) — bumped from the shared default of 32px — smaller than even one row — to a real multi-row amount per caller: 99px, exactly 3 rows, for `TagScrollArea`; 92px, 2 rows, for the Tag Pool's chip area. Holding past 300ms instead starts continuous scrolling at a steady per-frame rate, for anyone without a trackpad/wheel who'd otherwise need to click repeatedly to get through more than a couple of rows.

**Bug 1 — clicking an arrow inside a `ResultCard` also flipped the card.** Switching the scroll trigger from a plain `onClick` to `onMouseDown`/`onMouseUp` (needed to detect a hold) dropped the arrow's only `stopPropagation()` call along with it — but a native `click` event *still* fires on its own after a mousedown+mouseup pair completes on the same element, regardless of what those two handlers do, since each event type propagates independently. That unstopped click bubbled up to the card's own `onClick` and flipped it every time. Fixed by keeping a plain `onClick` on the arrow too, doing nothing but `stopPropagation()` — the actual scroll logic stays entirely in the press handlers.

**Bug 2 — holding one arrow to a scroll boundary, then immediately holding the opposite arrow, silently did nothing.** Reaching the boundary while holding unmounts *that* arrow's own button (`showTopGradient`/`showBottomGradient` flips false the instant `atTop`/`atBottom` does), so its `onMouseUp`/`onMouseLeave` can never fire to stop the loop it started — there's no longer an element for the browser to dispatch the release to. The old loop kept running in the background; starting a new one for the opposite direction didn't cancel it, so both ran simultaneously and visibly cancelled each other out. Two-part fix: `startContinuousScroll` now unconditionally calls `stopContinuousScroll()` before starting a new loop (defensive, regardless of what caused the previous one to be stuck), and the actual release-catching moved to a `window`-level `mouseup`/`touchend` listener registered only while a loop is active — a window listener fires regardless of what element is (or isn't) under the cursor when the release happens. Getting this listener's add/remove to actually pair up required care: `stopContinuousScroll` is a `useCallback` (not a plain function) so it's the same reference on every render for `removeEventListener` to match, and it reads *which* listener to remove from a ref (`globalReleaseListener.current`) rather than referencing itself by name inside its own body — the latter works at runtime but trips this project's stricter lint rule against self-referencing callbacks. Both bugs were confirmed live before and after the fix — the first via a scripted click that checked the card's flip transform, the second via holding one arrow to the measured scroll boundary, releasing, and confirming the opposite arrow's hold actually reduced `scrollTop`.

## Tag pool Level + Sort filters

Two global preferences, independent of each other, applying identically to the tag pool *and* result cards:

- **Level** (`LevelSelector.tsx`, segmented-button structure like `MatchSelector`) — which tags are visible: Level 1 "Casual" (only `isGenre: true`), Level 2 "Seasoned" (`avgRank ≥ 70` AND `seriesCount ≥ 5%` of the catalog — `POPULAR_AVG_RANK_THRESHOLD`/`POPULAR_SERIES_COUNT_PCT` in `config.ts`), Level 3 "Otaku" (`avgRank ≥ 40`, the pre-existing baseline). These labels are purely cosmetic — the underlying `LevelKey` values ("1"/"2"/"3") and every threshold/comparison are unchanged; only `LEVEL_OPTIONS`' display `label` (plus a supporting `hint` string — "light enjoyer" / "not my first rodeo" / "power level > 9000") changed. Genres always pass every level (`isTagVisibleAtLevel` in `tagPool.ts` short-circuits on `isGenre` before any threshold check). Each `hint` shows via the same hover-subtext pattern documented above (`LevelSelector` adopted the same hover-subtext pattern, replacing its own `title` tooltips) — not shown for only the active selection, previewable on any segment via hover. (A per-segment native `title`-tooltip version was tried at one point and reverted back to this hover-subtext mechanism — see the corrected "Tag pool header layout" section below, which used to describe that since-reverted intermediate state.)
- **Sort** (`SortSelect.tsx`, a native `<select>` — see below) — Popular/Unpopular (`seriesCount` desc/asc), A-Z, Z-A. Applied *within* each Theme subsection (not flattened across them) — sort reorders a group's contents, it doesn't restructure the section hierarchy.

Level decides *which* tags show; sort decides *what order* — the two compose independently (`tagsForCategories(...)` filters by level, a separate `sortTags(...)` call orders the result), and there's no hidden scoring: since a tag can only ever be selected if it's currently visible, `scoring.ts` needed zero changes — results are naturally scoped to whatever's selectable at the current level.

**Persistence** (`tagPoolPrefs.ts`, `components/konomi/`): a `useSyncExternalStore` + localStorage pattern, generalized to two global (not per-key) values — `useLevel()`/`useSort()` for reading, `setLevelPref()`/`setSortPref()` for writing. This is a genuine constraint, not just a style choice: an earlier version tried reading localStorage in a `useEffect` on mount and dispatching a correction into `useKonomi`'s reducer, which is exactly the `react-hooks/set-state-in-effect` anti-pattern this project keeps hitting and avoiding elsewhere too (the now-deleted `CollapsibleSection`'s expand state used the same external-store shape for the same reason; `TagPoolBody`'s active-tab fallback avoids a live instance of this same anti-pattern by computing the fallback at render time instead — see "Tag Pool hierarchy" above) — moving level/sort out to their own external store (read during render via `useSyncExternalStore`, written from event handlers, never from an effect body) avoids it entirely.

**The level-change deselect edge case**: switching to a level that no longer shows a selected tag must behave exactly like manually deselecting it — cleared from its mixer slot, no longer influencing results, with zero other side effects. `useKonomi` exposes a generic `pruneTags(visible: Set<string>)` action (it doesn't know what a "level" is, just which names remain allowed) that's structurally identical to `TOGGLE_TAG`: it only ever touches `slots`, never `results`/`generated`. Whatever cards are currently showing (if any) stay exactly as they are — a pruned tag's score contribution and chip highlight disappear immediately since `ResultCard` recomputes both live off `selectedTags` on every render, not because the result set changed. Results only regenerate when the user explicitly hits RECOMMEND again, same as any other manual unselect, including the all-selected-tags-pruned case (that's not special-cased into a `clearRecs()` either — it leaves cards on screen at "0/0", exactly like manually removing your last tag while results are up already does). `KonomiApp` is the one place that composes this: its level-change handler calls `setLevelPref()` *and* computes the new visible set to pass into `pruneTags()` — the only reason `KonomiApp` needs to know about levels at all, everywhere else just reads/displays the current value.

**Result cards** (`ResultCard.tsx`) apply the identical level filter + sort to their own tag chip list (via the `tagInfoByName` lookup — `useKonomi`'s former `tagRank: Map<string, number>` was widened to a full `Map<string, TagInfo>` since level-filtering needs `isGenre`/`seriesCount`, not just `avgRank`) — a card never shows a tag the pool wouldn't currently let you select.

**`visiblePoolTagNames()`** (`tagPool.ts`) is the canonical definition of "visible in the pool at this level," and both the level-change prune cascade and Random ×3 use it rather than `isTagVisibleAtLevel` directly. The distinction matters: `isTagVisibleAtLevel` only checks a tag's own rank/count against the level, so a Technical- or Sexual Content-category tag could pass it at Level 2/3 despite never being mapped into any `TAG_SECTIONS` entry (those two categories are intentionally excluded from the pool entirely, at every level). `visiblePoolTagNames` unions `tagsForSection(...)` across every real section instead, so it can never produce a name the pool itself wouldn't render — closing a gap an earlier pass left in place (both surfaces used the looser per-tag check until this pass).

**Hidden (not shown as a disabled tab) empty sections**: a section with zero tags at the current level (e.g. every non-Genres section at Level 1) isn't rendered as a tab at all, rather than showing a tab you can't do anything with. This is a pure render guard in `TagPoolBody` (`visibleSections`, filtered from `TAG_SECTIONS` each render) — see "Tag Pool hierarchy" above for what happens when the *currently active* section is the one that disappears.

## `SortSelect`: back to a native select, deliberately, not a regression

`SortSelect` went segmented-button → native `<select>` → segmented-button → native `<select>` again, and each move had a real reason, not just taste. It shipped first as a native select (`appearance-none` plus an overlay `▾`), got replaced with a `MatchSelector`/`LevelSelector`-style segmented row so the two Tag Pool controls shared one visual pattern, and has now moved back to a native select. What changed between the second and third move: `LevelSelector` no longer has a hint that needs visual-pattern parity with `SortSelect` to look consistent (see below — the hint moved to per-segment tooltips), so "the two controls should look alike" stopped being a reason to keep Sort as segmented buttons. A 4-option dropdown is also more compact than 4 segmented buttons, which fits the broader goal of these controls competing less for visual weight. The restyling approach is the same one this file already flagged as the right starting point if a select ever came back: `appearance-none` to strip the native arrow, plus a custom `▾` overlay (`SortSelect.tsx`) matching this app's own bordered/`elev-2` box treatment rather than each browser's native dropdown chrome. `min-w-[128px]` keeps the box a constant width across all four options ("Unpopular" is the longest) — without it, some browsers resize the box to match whichever option is currently selected, which reads as jumpy.

**`LevelSelector`'s hint moved from a shared line under the row to a per-segment `title` tooltip.** The previous version rendered whichever level's hint was *currently active* once, on a line below the whole row, deliberately not position-tracking so it stayed visually stable as the level changed. That's gone — each segment now carries its own hint as a native `title` attribute (`option.hint`), so hovering *any* segment (not just the active one) previews its hint, and there's no more absolutely-positioned line to center against, reserve clearance for, or keep from overlapping the section below. This considerably simplifies the header layout below, which used to carry a fair amount of complexity specifically to accommodate that hint line.

### Tag Pool and Recommendations became two tabs of one shared panel — since retired in favor of edit mode

This section used to document `PanelToggleHeader.tsx` and `TagPoolRecommendationsPanel.tsx`: a Recommendations/Tag Pool toggle that was the two section titles themselves, swapping in each tab's own contextual controls, both bodies always mounted with a `hidden`-class toggle between them, `activeTab` state lifted to `KonomiApp` so RECOMMEND could force it back to Recommendations. **Both files are deleted; nothing described that way exists anymore.** Results are now the app's single persistent main surface (`ResultsHeader.tsx` + `RecommendationsBody`, always rendered, no tab to toggle away from), and the tag pool is summoned on demand into `MixerBar`'s edit mode instead of living as a peer tab — see "MixerBar" below for the full replacement, including exactly where each retired piece (the resultsHint/Clear✕ cluster, Level/Sort, the "drag or tap to load a slot" hint, the always-mounted/hidden-toggle trick for preserving scroll state) ended up.

### Title rows: the `h2` and its companion span must be tightened together

Both section titles pair a `font-display` (Anton) `h2` with a `font-body` companion span carrying the Japanese label (`ミックス` for Mixer, `タグ` for Tag Pool). Anton's default line-height carries a lot of built-in leading — that's why `h2` gets `leading-[var(--leading-display)]` (0.86). But tightening only the `h2` fixes the row exactly until the *other* element becomes the tall one: Tag Pool's `h2` was tightened in an earlier pass while its `タグ` span was left at the browser default (~1.4-1.6× for `font-body`), so the span silently took over as the row's tallest child and reintroduced the same visual "extra space above the title" symptom from a different source — a same-line sibling swapping in for the wrap-clearance box in the four instances above, but the identical underlying mistake: whichever child has the tallest *line box* dictates the row's rendered height, regardless of which child visually looks like "the title."

Fixed by tightening **both** elements of every title row: `h2` keeps `leading-[var(--leading-display)]` (0.86, calibrated for Anton's all-caps Latin glyphs), and the companion span gets `leading-[var(--leading-tight)]` (1.05) rather than reusing `leading-display` — 0.86 is tuned for Anton specifically, and applying that same aggressive a ratio to a CJK `font-body` span risks visually clipping full-width katakana glyphs, which have different vertical metrics than Latin caps. `leading-tight` is the existing, more conservative token already used elsewhere for body-text titles (`ResultCard`'s `h3`, `TagSlot`'s tag text), and confirmed live afterward to render `ミックス`/`タグ` cleanly with no clipping or cramping at either section's title size.

**This only fully closes the gap when the title row's height is what determines the row's rendered position.** Re-measured live (`section top → title row top → h2 own box top → h2 ink top` decomposition) after tightening both elements in each row: Mixer's visual top gap shrank from ~32-33px to ~29.5px, closely tracking the ~26px raw padding — the ~3.5px residual is `items-center` centering the (now-short) title row against the taller locked-count badge (`{lockedLabel}`) sharing its flex row, a legitimate centering effect rather than leftover leading slop. Tag Pool's visual top gap, however, stayed at ~32px, essentially unchanged, because Tag Pool's outer header row (`flex items-center justify-between`, see above) centers the *title block* against the *Sort/Level controls block*, and the controls block (~36.5px tall) is taller than even a fully leading-tightened title block (~22.4px) — the ~7px residual there comes entirely from that cross-block centering, a mechanism this leading fix cannot touch (tightening the title further, if anything, *widens* this particular gap, since a shorter title gets centered with a larger offset against the same taller controls block). Closing Tag Pool's remaining gap would mean changing how the outer row aligns those two blocks against each other — a separate, deliberate decision from the "Tag Pool header layout" section above, not a title-leading problem.

The reusable rule going forward: **any title row pairing a display `h2` with a companion span needs `leading-display` on the `h2` and `leading-tight` on the span, applied together, every time** — never just one. But also check whether anything *else* sharing that row or a parent row (a badge, a controls block being centered against it) is taller than the now-tightened title; if so, the remaining visual gap belongs to that other element's alignment, not to the title's typography.

## Recommendations layout — a shared height token, and a small-viewport carousel

### The empty-state placeholder and `ResultCard` share `--result-card-height`, not a duplicated measurement

The "MIX TAGS" empty-state box and every `ResultCard` must render at the exact same height, or the page visibly jumps the instant results replace the placeholder. This is one of the rare cases documented above ("What's intentionally *not* tokenized") where a component-specific dimension *is* pulled into a real token, specifically because two independent components need the same value and must never drift apart — hardcoding `421px` as a literal in both places would work today but silently break the moment either one changes without the other being updated in lockstep.

The mechanism is a plain CSS custom property (`--result-card-height` in `globals.css`'s `:root`), not a shared JS/TS constant, for a specific reason: Tailwind's class scanner needs the *complete* arbitrary-value class to appear as static text to generate CSS for it, and the two consumers need different prefixes (`ResultCard` needs `h-[…]`, the empty state needs `min-h-[…]`) — a shared TS constant interpolated into a template literal (`` `h-[${N}px]` ``) wouldn't be visible to that scanner as a complete literal, so Tailwind wouldn't generate the rule. `var(--result-card-height)` sidesteps this entirely: the literal text `h-[var(--result-card-height)]` / `min-h-[var(--result-card-height)]` is what Tailwind sees (satisfying its scanner), while the *value* itself is resolved once, at the CSS level, from a single declaration. A "measure the grid's rendered height at runtime" approach was also considered and rejected — it doesn't actually work here, since there's nothing to measure at the exact moment the value is needed (the empty state, by definition, has zero `ResultCard`s in the DOM to inspect).

The empty-state box also switched from padding-establishes-height (`py-[var(--space-huge)]`, sized to fit its own content) to `min-h-[var(--result-card-height)]` + `flex flex-col items-center justify-center` — padding alone doesn't grow to fill leftover `min-height` space, so a real centering mechanism was needed once the box's height stopped being purely content-driven.

### One-viewport-fit: a best-effort target now, not an enforced guarantee — and why `--result-card-height`'s clamp grew three more tokens

`--result-card-height` is also a `clamp(322px, calc(100svh − …), 445px)` — the "preferred" middle term sizes the card so the masthead+header+card+mixer group fills whatever's left of one viewport, so that when the group *does* fit, the page needs no scroll to see all of it. This clamp originally only subtracted `--header-row-height` and `--mixer-bar-height` from `100svh` — a real, confirmed bug: it never accounted for the masthead's own height, its own bottom margin, or the page's own top/bottom padding (~247px, unbudgeted), so the group silently ran that far too tall at nearly every real viewport size, even though the *card itself* always looked correctly sized in isolation. Fixed by adding `--masthead-height` (a new token, same flat-conservative-constant treatment as `--mixer-bar-height` below) and the missing gap/padding terms to the same calc.

**Even corrected, the group can't always fit — and that's now accepted, not fought.** At real phone heights, the card pins to its 322px floor and the total still overflows past the viewport (confirmed live: 375×667 overflows by ~125px even with the corrected formula). Earlier in this feature's life that would have been treated as a bug to keep chasing; the current, explicit decision is the opposite: **when it fits, great — scrolling past the masthead lands on a clean, one-screen view of the group; when it doesn't, the page just scrolls normally, no clamping, no clipping, no forced no-scroll behavior.** Concretely, this meant *removing*, not adding, several things that used to enforce the fit: `KonomiApp`'s own root div lost `min-h-screen` (was forcing the page to at least one viewport tall even when real content was shorter, stranding the leftover space as extra blank space below the mixer rather than distributing it — confirmed live, `bottomGap` dropped from 42.6px to exactly `pb-2xl`'s own 24px once removed); no scrollbar-forcing CSS was kept either (see below).

**`--mixer-bar-height` used to be a 4-tier width-breakpoint ladder (`<351px`/`351–639px`/`640–992px`/`993–1023px`/`≥1024px`); it's a single flat `185px` now.** The ladder was real (mixer's own content genuinely changes height at those widths — 640px/993px are the same RECOMMEND-text and Row-3-text thresholds documented below), but it fed directly into a value a classic scrollbar's own ~15-17px width consumption could step across, at the exact widths near each breakpoint — a real, confirmed reflow loop: scrollbar appears → available width shrinks → steps `--mixer-bar-height` to a shorter tier → `--result-card-height`'s clamp shrinks the required total → page no longer overflows → scrollbar disappears → width grows back → steps the tier back up → overflows again. Two CSS-only mitigations were tried and reverted first — `scrollbar-gutter: stable` (produced a visible reserved-but-unpainted band on the page's own edge, and reportedly didn't fully stop the toggle either) and a forced `overflow-y: scroll` on `html` (closed the visible gap but was still compensating for the loop rather than removing it) — before landing on the actual fix: since this token is *only* ever an estimate fed into a sibling's clamp formula (nothing applies it as a real height on `MixerBar` itself, which already just sizes to its own natural content), there was no need to track it precisely across width at all. A single flat constant — the true max across every in-scope (≥375px) tier, `185px` — removes the width-dependency entirely, with no JS/`ResizeObserver`/hysteresis needed. Same trade-off as `--masthead-height` below: the card computes a little smaller than the theoretical optimum at narrower widths where the real mixer is shorter than 185px (unclaimed blank space above the mixer, not a functional bug), in exchange for a variable nothing can toggle.

**`--masthead-height` (170px) is the same flat-conservative-constant idea, for the same structural reason `--result-card-height` itself is a token and not a duplicated literal** (see above) — except here, nothing else needs to *match* this value exactly; it only needs to be a safe upper bound so the clamp above never under-budgets. `Masthead.tsx`'s own real height varies with width (a plateau around 167-169px across most of the ≥375px range, dropping to ~128px in a 460-1024px band once its top row fits on one line without wrapping, climbing again past ~1024px as its wordmark's own `clamp(44px, 8vw, 78px)` keeps scaling) — 170px is the measured max across that whole range, not a per-width ladder, for the identical reason `--mixer-bar-height` gave up its own ladder above: this value only feeds a sibling's estimate, so precision beyond "never too small" buys nothing.

**The page background (and its dotted halftone texture) also moved off `KonomiApp`'s own root div, onto `html`, during this same investigation — a related but distinct bug.** Once that div's `overflow-x-hidden` was found to be silently forcing `overflow-y: auto` on it too (a real CSS spec rule: one non-`visible` axis forces the other axis's *used* value off `visible` if it wasn't explicitly set) — making it an accidental, unintended nested scroll container, confirmed live via a real wheel-scroll moving *that div's* `scrollTop` instead of `window.scrollY` — its own background could fall short of the *actual* scrollable canvas once it stopped being the true scroll root. Fixed two ways together: `overflow-x-clip` (not `-hidden`, which doesn't trigger the same legacy pairing rule) restores `html`/`body` as the one real scroll root, and the background (`background-color` + the halftone `background-image`, `SHOW_HALFTONE`-gated via a `data-halftone` attribute) moved onto `html` itself, which gets a special CSS treatment no regular element does: the root element's own background always paints the *whole* scrollable canvas, regardless of its own box height — a guarantee immune to any future height-mismatch, rather than a background that merely needs to happen to be tall enough. `html` also needs its own `data-theme="default"` now (matching `useKonomi`'s real initial state, so there's no hydration flash) — `--bg`/`--muted` are theme-scoped custom properties that only resolve on an element that itself carries `data-theme`, and inheritance is descendant-only. `KonomiApp`'s own div still carries `data-theme` too (unchanged), kept in sync onto `html` via a `useEffect` in `KonomiApp.tsx` on every subsequent theme change.

### Below 1152px, results become a single-row snap carousel instead of a wrapping grid

`grid-cols-[repeat(auto-fill,minmax(208px,1fr))]` doesn't drop straight from "all cards on one row" to "one column" as it narrows — `auto-fill` keeps fitting as many 208px-minimum columns as it can at every width in between, wrapping into 2, then 3+ rows well before it ever reaches a single column. A `max-[1152px]:` variant switches the results container from `grid` to `flex overflow-x-auto snap-x snap-mandatory` (each `ResultCard` gets `max-[1152px]:flex-none max-[1152px]:w-[85%] max-[1152px]:snap-start`), where **1152px = 5×208px (`DEFAULT_RESULT_COUNT` × the grid's min column width) + 4×16px (`gap-xl` between them) + 48px (the page's own `px-2xl` margins)** — the width where all 5 result cards stop fitting on a single grid row. Confirmed live via 1px-step bisection: exactly 1 row at 1152px, 2 rows at 1151px.

**This replaced an earlier, wrong choice of 480px** (the grid's own natural *1-column* breakpoint) — confirmed live, after a bug report, that it didn't work: from 480px up to 1152px, the grid was already wrapping into 2–3 rows the whole time (e.g. 3 rows at a 700px viewport), so a carousel that only kicked in below 480px left most of the practical resize range still wrapping into multiple rows — defeating the entire point of building this (stay a single row, keep the mixer co-visible without scrolling past a tall stack of cards). 480px had seemed like the more conservative, "small breakpoint"-shaped choice at the time and was picked specifically to *avoid* coupling to `DEFAULT_RESULT_COUNT` — but avoiding that coupling doesn't matter if the result doesn't actually solve the stated problem. **1152px is coupled to `DEFAULT_RESULT_COUNT` (`config.ts`) and needs re-deriving (5×208 + 4×16 + 48) if that count ever changes** — an accepted, documented tradeoff now, not an oversight.

### Card width steps down through 4 tiers — not one fixed "85%" for the whole carousel range

The first version sized every carousel card at a flat 85% of the row — reasonable at the narrowest widths, but confirmed live to look wrong at 1152px down to ~1000px, where 85% of a wide row produces one enormous card when 4 comfortably-sized ones would easily fit. `ResultCard` now steps through 4 width tiers as the row narrows, aiming for 4 cards, then 3, then 2, and only falling back to one dominant card once 2 no longer fit at a reasonable size:

| Tier | Width (% of row) | Applies at (viewport) |
|---|---|---|
| ~4 cards | 22% | 993px–1152px |
| ~3 cards | 30% | 741px–992px |
| ~2 cards | 46% | 501px–740px |
| 1 card (fallback) | 85% | ≤500px |

Percentages, not fixed pixels, so card size still flexes smoothly within a tier instead of jumping — only the *step count* changes at each boundary, confirmed live via a `visibleFull`-card count check across the whole range (4 → 3 → 2 → 1, matching the table).

**Tailwind v4 compiles `max-[Npx]` as strictly-less-than (`@media not (min-width: Npx)`), not "Npx or narrower."** The first version of these tiers paired each tier's bound as `min-[741px]:max-[992px]`, `min-[993px]:max-[1152px]`, etc. — assuming `max-[992px]` meant "≤992," which left a genuine 1px gap at every exact boundary (992, 740, 500) where *neither* tier's compound variant matched, collapsing the card to `width: 0` (confirmed by inspecting the actual generated `@media` rules live, not just guessing from the symptom). The fix: each tier's `max` bound is set to the *exact same number* as the next tier's `min` bound (not `min − 1`) — e.g. `min-[741px]:max-[993px]` paired against `min-[993px]:max-[1152px]` — so the exclusive/inclusive pairing meets with zero gap and zero overlap. Each tier also pairs a real `min` *and* `max` (not a bare `max-[Npx]`, which nests/overlaps with every wider tier's rule and would apply simultaneously at narrow widths, same class of bug the very first carousel breakpoint mistake also stemmed from).

### Alignment: mostly left, not dead-centered — `snap-start` + `scroll-padding-left`, not `snap-center`

Every `ResultCard` uses `snap-start`, and the row itself carries `[scroll-padding-left:6%]`. `snap-center` was tried and explicitly rejected: true centering reads as a different, more "look at one thing in isolation" carousel feel than wanted here — the active card should still sit mostly left-aligned, the way it did before, just with enough of a shift that the previous card visibly peeks in too.

The mechanism: `scroll-padding-left` doesn't change *whether* a card centers, it changes *where* "start" is measured from — a `snap-start` card comes to rest 6% of the row's width in from the true left edge, rather than flush against it, and that 6% gap is exactly filled by a sliver of the previous card. The very first card needs no special-casing: there's nothing before it to scroll to, so the browser clamps `scrollLeft` at 0 and it sits genuinely flush-left on its own, giving the "first card only peeks right" behavior for free. Confirmed live via screenshots at the first, a middle, and the last card: first card flush-left with only a right peek, middle cards showing slivers on *both* sides, last card flush-right with only a left peek.

### Arrow affordance, peek, and reset-on-RECOMMEND all now come from `ScrollFadeArea`, not a bespoke implementation

This used to be a fully custom implementation, specifically because `ScrollFadeArea` was vertical-only at the time it was built. Once `ScrollFadeArea` gained a real horizontal orientation (for the Tag Pool's section tab strip — see "Tag Pool hierarchy" above), the carousel's mechanics turned out to generalize cleanly onto it too; see that section for the full list of props this needed (`getScrollStep`, `scrollResetKey`, `arrowWidth`/`arrowHeight`/`arrowShadow`/`arrowInset`, `scrollPaddingStart`) and what still doesn't transfer (the grid↔carousel breakpoint switch, which stays in `RecommendationsBody`'s own row markup). Summarizing what's specific to this caller:

**Arrows are bigger (36×36) and shadowed**, not `ScrollFadeArea`'s small (18×16) flat default — to read clearly against a card several hundred px tall (`--result-card-height`, currently 445px), and because they sit over arbitrary cover art rather than a flat surface color (same reasoning as the swap-icon hint chip's own background), inset from the row's edge by `var(--space-md)` (`arrowInset`) rather than flush against it. **`arrowHeight={36}` had been missing since this was first built** — only `arrowWidth={36}` was ever passed, so `IconButton`'s `height ?? width` fallback never applied (an explicit `arrowHeight` prop, defaulting to 16, was always being passed down, just never overridden here) and these arrows silently rendered as a 36×16 rectangle instead of the intended 36×36 square for the entire time this component has existed — confirmed via `git log -p`, not assumed. Fixed by adding the missing prop; a one-line fix once traced, but the *symptom* (arrows looking visually "off," proportionally wrong for a tall card) had been live and unnoticed until directly compared side-by-side against `SectionTabStrip`'s own correctly-sized small arrows.

**Hover-reveal on `TagScrollArea`'s own arrows (inside each card) is scoped separately from the carousel's, via a second named group, `reveal-nested`** — see `RevealGroup` in `IconButton.tsx`. `TagScrollArea`'s `ScrollFadeArea` is nested *inside* the results carousel's own `ScrollFadeArea` (each card, containing its own tag area, is a child of the carousel's row), and both originally used the same default hover-reveal group name (`reveal`). Since Tailwind's `group-hover/reveal:` compiles to a plain CSS descendant selector (`.group\/reveal:hover .the-utility`), it matches whenever *any* ancestor carrying that class is hovered — not specifically the nearest one — so hovering anywhere in the outer carousel (the title of a card, its cover art, anywhere) satisfied the hover-reveal condition for *every* card's nested tag-scroll arrows simultaneously, confirmed live: hovering one card's title revealed all five visible cards' arrows at once, not just that card's own. `TagScrollArea` now passes `groupName="reveal-nested"` to its `ScrollFadeArea`, a second complete-literal group name `IconButton`/`ScrollFadeArea` both recognize — since sibling cards don't share an ancestor relationship with each other, each card's own tag-area hover is now correctly independent of every other card's, and independent of the outer carousel's own (still-`reveal`-named) arrows. Confirmed live: hovering a card's title no longer reveals any tag-scroll arrow; hovering that specific card's tag area reveals only its own.

**A click scrolls by the *current* card's live-measured width plus the row's gap** (`getScrollStep`), not a fixed pixel step — card width isn't constant, it steps through the 4 tiers above — and doesn't need to be pixel-exact, since `snap-mandatory` corrects any `scrollBy` amount to the nearest real snap point regardless. `getScrollStep` reads off a plain `rowRef` this component still keeps for exactly that measurement — `ScrollFadeArea` deliberately doesn't expose its own internal scroll element to callers, so this ref points at `ScrollFadeArea`'s *children* (the grid/carousel row itself), not its viewport.

**`recommendGen` (in `useKonomi.ts`) resets the carousel's scroll position on a fresh RECOMMEND, but not on a single-card swap** — passed straight through as `scrollResetKey={recommendGen}`. Both actions produce a new `results` array reference, so `results` itself can't distinguish "a whole new batch, scroll back to the start" from "one card changed, leave the viewport where it is." `recommendGen` is a counter bumped only on `recommend()`'s success path (not its two error early-returns, since an errored RECOMMEND leaves `results` completely untouched) and never touched by `replaceCard()` (swap) — confirmed live that a swap leaves `scrollLeft` exactly where it was, while a fresh RECOMMEND resets it to `0`.

**A bonus that came along for free, not something explicitly asked for:** press-and-hold-to-continuously-scroll and mousewheel-to-horizontal-scroll, both inherent to `ScrollFadeArea`'s horizontal mode now, neither of which the bespoke implementation had. Native trackpad/touch scrolling and drag-vs-scroll input routing were already free before (standard "orthogonal nested scroll containers" browser behavior — `TagChip`'s HTML5 `draggable` drag never contends with either gesture) and remain unaffected by the migration.

### `ScrollFadeArea`'s viewport is now unconditionally non-`visible` overflow, so the shadow-clipping fix had to become unconditional too

Each `ResultCard` uses `shadow-[var(--elev-4)]` — a flat, blur-free `5px 5px 0 var(--ink)` offset, bleeding only past the card's own bottom and right edges. The original bug: setting only `overflow-x` on the scrolling row (below the 1152px carousel breakpoint) silently coerced `overflow-y` from `visible` to `auto` too (a real, easy-to-miss CSS rule — see below), clipping every card's shadow at the row's own bottom/right edge. Above 1152px, the row was a plain `grid` with no `overflow` set at all, so the shadow painted fine there.

**Migrating onto `ScrollFadeArea` changed which widths are at risk.** `ScrollFadeArea`'s horizontal viewport is *always* `overflow-x-auto overflow-y-hidden`, regardless of breakpoint — both axes explicitly non-`visible`, which is enough on its own to clip a child's shadow bleed at that edge, with or without the coercion rule now involved. That means the fix (padding the row to give the clipped overflow room to paint the shadow, then canceling the added size with a matching negative margin) has to be **unconditional now too** (`pr-[5px] pb-[5px]` on the row, `-mr-[5px] -mb-[5px]` on the wrapper around `ScrollFadeArea`) — not `max-[1152px]:`-gated the way the old bespoke version was. Confirmed live this doesn't introduce a new problem in grid mode: a CSS grid container's own padding doesn't expand its rendered outer width past its box the way a block/flex wrapper's does (its `1fr` columns just adapt to whatever's left inside the padded content box), so `pr-[5px]`/`pb-[5px]` never trips a false-positive `hasOverflow` above 1152px — grid mode's `scrollWidth`/`clientWidth` measured identically before and after.

**The underlying CSS rule, for reference:** if exactly one of `overflow-x`/`overflow-y` computes to something other than `visible`, the other one's `visible` is *itself* computed as `auto`, regardless of whether it was left at its default or explicitly re-declared `visible` — the rule keys off the resulting value, not how it got there. This is what caused the *original* version of this bug (only `overflow-x` set, below 1152px); `ScrollFadeArea`'s explicit `overflow-y-hidden` sidesteps that specific coercion but reintroduces the same clipping outcome by a more direct route (an explicitly non-visible axis, not a coerced one).

**The negative margin needed real containment**, and where that containment lives changed with the migration too. `RecommendationsBody` still returns a `<div className="flow-root">` (a new block formatting context) rather than a bare Fragment — without it, `-mb-[5px]`/`-mr-[5px]` would collapse straight through `TagPoolRecommendationsPanel`'s wrapper divs and eat into *that* component's own `mb-[var(--space-3xl)]` section margin instead of stopping at the padding it was meant to cancel (confirmed live as a real regression the first time this fix was built, before the migration: 32px measured as 27px). Confirmed live after the migration: the section-to-section gap still measures a clean 32px, and the shadow still renders fully at every carousel breakpoint (900/480px) and in grid mode (1400px), with the padding neither lost nor double-applied in the move to `ScrollFadeArea`.

### `ResultCard`'s cover + tag area: one shared filmstrip now, at every card size — no height gate, no `COVER_HEIGHT_PX`

Two rounds, not one. Round one (superseded, see below) gave short cards (below a `[@media(min-height:731px)]` gate) a real cover continuation instead of a flat blurred stand-in, but only below that gate — above it, a separate, older reflection mechanism (its own two `<img>`s, positioned via a hardcoded `COVER_HEIGHT_PX` offset) still owned the tag area, and cover-box still had its own independent `<Image>`. Round two unified both into one mechanism, at every card size, with no breakpoint anywhere in this file anymore.

**The insight that made unification possible: the *existing* reflection never actually used `object-fit: cover` for its own two images.** It rendered the whole, uncropped cover at natural scale (`width:100%; height:auto` — `object-fit` can't do this, hence plain `<img>`, not `next/image`), then stacked a mirrored copy directly below it in normal block flow. The seam between real content and mirror was automatically correct — wherever the first, full-height image's own natural rendering happened to end — because nothing was cropped independently of anything else. That same idea generalizes to the sharp top crop too: one absolutely-positioned filmstrip (continuation image, then mirror image, stacked exactly as the old reflection already did), positioned at `top: 0` against `FRONT` itself (cover-box's and tag-wrapper's shared parent, otherwise containing only those two), no offset, auto height. Each box's own existing `overflow-hidden` window reveals whichever slice of this one filmstrip falls inside it: cover-box's window shows the filmstrip's own top, at natural width-scale (visually identical to what its previous independent `object-fit: cover` crop rendered, since portrait cover art at this card's own width makes that crop width-driven, not height-driven — confirmed directly against the real source now, not just inferred: AniList's own "medium" cover tier, 230px wide, ~320–345px tall, aspect ~0.67–0.72). Tag-wrapper's window picks up exactly where that leaves off — real, continuing content for as long as the source hasn't run out, becoming the mirror automatically the instant it has, since that's simply further down the same stacked filmstrip. No breakpoint anywhere: the transition is a property of the filmstrip's own layout, not something computed against the viewport, so it's correct continuously, at any card height.

**Cover-box's own `<Image>` is gone, not just left alone this time — the filmstrip is now the only place the cover image renders from at all.** That required two things round one didn't need: cover-box's `bg-[var(--fill)]` moved to the filmstrip's own wrapper (as its loading-placeholder color — the same role, just relocated to where the image itself now lives; an unconditional `bg-[var(--fill)]` staying on cover-box would hide the filmstrip completely, defeating the whole point), and cover-box's own fallback condition became `!hasImage || reflectionBroken` (previously just `!hasImage` — a broken cover URL used to still attempt cover-box's own independent, now-removed `<Image>` and likely show a raw broken-image icon there; routing failure through the same `reflectionBroken` state everyone else already used makes this more consistent, not less).

**Verified three separate ways, not just reasoned through:** (1) An *isolated* comparison — same known cover URL, rendered via `object-fit: cover` in one box vs. the natural-scale-filmstrip technique in an identically-sized sibling box, at all four carousel width tiers (real card widths measured live: ~240/252/272/332px) and two height scenarios each. Pixel-diffed with `sharp`: near-zero at the shorter height, a small (~2–3% average byte delta) but visually-imperceptible difference at the taller height, consistent with ordinary sub-pixel rasterization rounding between the two techniques (the same class of artifact this file's own filmstrip mirror-seam fix, `marginTop: -3`, already exists to paper over elsewhere) — not a different crop. Confirmed by eye, side by side: indistinguishable. (2) A *live app* pixel-diff was tried first and discarded as invalid: `scoring.ts` picks results with `Math.random()`, so two separate page loads with the identical tag selection can still surface entirely different covers — a 90%+ byte delta there was two different anime, not a regression. (3) Measured the filmstrip's own real, natural rendered height against real covers at the widest carousel tier (332px cards) — ~460–510px per copy, ~500px+ of margin over the card's own ~380–445px real height range — confirming "room to spare" isn't a narrow margin anywhere in this app's actual size range, carousel or grid mode alike (grid mode's own narrower ~217px cards checked too: the mirror does visibly kick in there, correctly, roughly the bottom half of the tag area on a tall viewport).

**Reused, not reinvented:** the continuation scrim (from round one) is now unconditional rather than gated — the seam always exists, at every size, so there's no case left where it would double up with anything else. The veil (`--cover-reflection-veil`) needed no changes at all; it was never gated by height even in round one.

**The generalized tell, refined from round one's own version of it: when several boxes need to look like one continuous image but must stay independently sized for layout reasons, don't crop each one separately and align the crops with math (a hardcoded offset like the old `COVER_HEIGHT_PX`, valid at exactly one size) — give one shared, unclipped, natural-scale layer the combined space instead, and let each box's own existing clipping reveal its own slice of it.** The boxes never need to agree on a coordinate system, and the transition between "real content" and "whatever comes after" (here, a mirror; conceivably anything else stacked the same way) falls out of ordinary document flow instead of being computed against anything external.

**Round three: the filmstrip's own mirror image regressed `TagScrollArea`'s touch-drag scroll, real-iOS-only — and the first fix attempt (`touch-none` on the filmstrip) was wrong, confirmed live.** Reported live, only on real Safari/Chrome-iOS (both — same underlying WebKit) — doesn't reproduce in headless or emulated Chromium at all. A plain `elementFromPoint()` at the touch coordinate already resolves correctly to `TagScrollArea`'s own scroll viewport, so this was never a DOM hit-testing bug the way the small-card continuation's own reveal-through mechanism was.

First attempt: added `pointer-events-none`/`touch-none` to the filmstrip wrapper, reasoning that the mirror image's `transform: scaleY(-1)` (needed for the flip, no non-transform way to do it in CSS) promotes it onto its own GPU compositing layer, and that a composited sibling overlapping a scroll container's region might confuse WebKit's own touch routing independent of `pointer-events`. **Confirmed live: did not fix it.**

The actual mechanism — and the fix — was already directly established earlier in this app, for a *different* scroll container: `RecommendationsBody`'s own carousel viewport (`scrollRef`, its horizontal `ScrollFadeArea`). That fix's own comment (`RecommendationsBody.tsx`) states the precise rule this round had lost sight of: **`pointer-events: none` disqualifies a scroll container from native touch-scroll-gesture-*chaining* entirely on real mobile WebKit, not just from click hit-testing — but only when it's on the scroll container's *own* structural elements**, not an unrelated sibling. `TagScrollArea`'s own viewport was never `pointer-events: none` here (confirmed `auto` throughout) — so disqualifying-property theories (both the original `touch-none` attempt and the closely-related "GPU layer" theory) were reasoning about the wrong element. The original carousel fix's actual resolution was **explicit z-index (paint order) instead of a disqualifying property** — Clear ✕ wins its own hit-test via `z-[var(--z-raised)]`, so the carousel's own `scrollRef`/`root`/`contentRef` could go back to plain `pointer-events: auto` and keep receiving the gesture.

Applied the same resolution here, not the same property: removed `pointer-events-none`/`touch-none` from the filmstrip entirely (never actually needed for hit-testing correctness — cover-box's own opaque `bg-[var(--fill)]` and tag-wrapper's own box already win there by DOM order regardless of the filmstrip's own pointer-events), and gave **tag-wrapper an explicit `z-[var(--z-raised)]`** (was implicit `z-index: auto` + later-DOM-order-wins) — explicit z-index creates tag-wrapper's own stacking context, isolating `TagScrollArea`'s gesture handling from whatever compositing the filmstrip's transform needs, rather than leaving both to share `FRONT`'s stacking context together. Verified structurally (computed `pointer-events: auto`/`touch-action: auto` on the filmstrip, `z-index: 0`/`1` respectively on filmstrip/tag-wrapper, hit-test still resolves correctly, lock-button toggle and tap-to-flip both still work) — the actual on-device effect still can't be confirmed outside a real iOS device, so this remains the leading hypothesis, just now backed by this app's own *confirmed*, not speculative, precedent.

**Audited for the same shape of risk elsewhere, per explicit request — found nothing else live:** `ScrollFadeArea`'s `disableWrapperPointerEvents` prop (the mechanism behind the original carousel bug) has no current callers at all — dormant, not a risk. `RecommendationsBody`'s own grid wrapper still carries `pointer-events-none` deliberately (a *different* wrapper than `scrollRef`, already reasoned through and documented there). The continuation scrim inside tag-wrapper (round one, this file) is also `pointer-events-none` and geometrically overlaps `TagScrollArea` — but it predates this regression (existed before the filmstrip/mirror), and is already safe on the same explicit-z-index logic: its own `z-[var(--z-raised)]` (1) loses to `TagScrollArea`'s wrapper's own `z-[2]`, so pointer-events-none there is redundant-but-harmless, not load-bearing. `MixerBar.tsx` has no `transform` usage at all. The one genuinely new risk this session introduced was the filmstrip's own always-mounted mirror transform — the thing just fixed.

## MixerBar — a sticky-bottom bar with a browse mode and an edit mode

`MixerSection` (a static, in-flow section) is now `MixerBar.tsx`, the last child of the page's own content column, always rendered. This supersedes the old Recommendations/Tag Pool tab toggle entirely (see "Tag Pool and Recommendations became two tabs… since retired" above): results are now the app's one persistent main surface, and the tag pool is *summoned* into this bar's edit mode rather than living as a peer tab.

**Three positioning eras, not two: `position: fixed` (Step 1), un-pinned to plain normal flow (Step 2), now `position: sticky; bottom-[space-2xl]` (Step 3)** — see "The single box that grows: how edit mode actually expands" below for the growth mechanism (unchanged across all three eras) and "`position: sticky` — floats when the page scrolls, rests in flow otherwise" below for what Step 3 changed and confirmed. This section documents the current shape only; earlier eras are intentionally not re-explained beyond what's needed to say why each was replaced.

### Browse mode and edit mode are one bar that grows, not two overlays

`KonomiApp` owns a single `editMode: boolean` (replacing the old `activeTab`, in the same place, for the same reason: `handleRecommend` needs to force it closed even when it's currently open, so RECOMMEND always lands the user back on the results it just produced, success or error). `MixerBar` renders three rows in a flex column, and edit mode only changes what's *between* the first and last of them — it never introduces a second, separate overlay:

1. **Pool panel** — `TagPoolBody` (its own combined tabs+filters row, then the chip area), present only in edit mode. Not a separate sheet — see "State preservation" below for why it's still always mounted regardless. Sits directly above the slots — not between the slots and controls, where an earlier version placed it (see below for why).
2. **Slots row** — the 3 `TagSlot`s, unchanged, always rendered.
3. **Controls row** — MIN TAG MATCH, Random, Clear, RECOMMEND, plus a Tag Pool/Done toggle. Everything below about this row's breakpoints and thresholds refers to it.

**No header row in either mode.** An earlier version had a fourth row above the pool panel — a title ("Mixer"/"Super Mixer" + JP subtitle) and an `X / 3` filled-count badge, in both modes, plus Level/Sort filters right-aligned in edit mode only. Removed entirely, not relocated, as a deliberate simplification — one less row of chrome, not a smaller version of it. Level/Sort didn't disappear with the rest of that row, though: they moved down into `TagPoolBody`'s own combined tabs+filters row instead (see "Level/Sort moved into the tabs row" below).

**Pool panel above the slots, not below them — one insertion point, not two.** An earlier version placed the pool panel *below* the slots (between slots and controls) — opening/closing edit mode then had to insert/remove that block in the middle of the bar, which additionally pushed the slots' own downstream neighbor (the controls row) to shift its position relative to the slots twice-removed. With the pool panel at the top instead, opening/closing edit mode only ever inserts/removes one block in one place; the slots row's own position relative to the bar's top never changes in either mode, and only the controls row shifts, exactly as far as the pool panel is currently tall — one visible change instead of a layout that could read as two independent, differently-timed shifts.

Tapping an *empty* slot or the "+ Tag Pool — tap to add tags" affordance (rendered in `KonomiApp`, below `RecommendationsBody`, always visible in browse mode) toggles edit mode — opens it if closed, *closes* it if already open (added after the fact: an empty slot used to only ever open, so tapping one again while already in edit mode was a silent no-op; it now mirrors Done ✓/click-outside exactly, giving a second, already-visible way to close, reachable without moving to the header). A *filled* slot still clears, unchanged either way. This decision is made inside `MixerBar` itself, not `TagSlot` or the reducer — it already receives both `slots` and `editMode`, so its own click-dispatch wraps each `TagSlot`'s handler as `(index) => slots[index] ? onSlotClick(index) : editMode ? onCloseEditMode() : onOpenEditMode()`, rather than threading a new prop through `TagSlot` or teaching the DOM-free `useKonomi` reducer about UI-only edit-mode state. Done ✓ always calls `onCloseEditMode` too, unchanged.

**RECOMMEND only closes edit mode on success — an error leaves the user in edit mode, not the collapsed bar.** This reverses an earlier, explicitly-flagged assumption (closing unconditionally, matching the old `activeTab` behavior) — on reflection, an error like "impossible-min" is something the user needs to *fix*, and fixing it means staying exactly where the tags and section tab already are, not getting bounced back to browse mode and having to reopen the sheet to try again. The mechanism: `useKonomi`'s exposed `recommend()` action now returns the resulting `MixerError` (or `null` on success) synchronously, rather than nothing — `KonomiApp.handleRecommend` only calls `setEditMode(false)` when that return value is falsy. A plain `dispatch` can't answer "did this just error" on its own, since the reducer's state update isn't visible until the next render; `recommend()` (the pure function inside `useKonomi.ts` computing the new state) is called directly against a `stateRef` mirror (kept current via an effect, for the same `react-hooks/refs` reason `MixerBar`'s own ref-mirrors are — see that comment) purely to extract `.error` synchronously, while the actual state update still goes through the normal `dispatch({ type: "RECOMMEND" })` path unchanged. This computes the pure `recommend` function twice per click (once for the synchronous answer, once inside the reducer) — a deliberately cheap, accepted duplication rather than restructuring how the reducer applies its own state, since this scores against a hobby-scale catalog, not a hot loop.

**This is only correct because `recommend` is pure — same `state` in, same output (and same `.error`) out, every time.** The two calls agree by construction *because* neither can see anything except its own `state` argument. If `recommend` ever gained a side effect or any non-determinism (a random tiebreak among equally-scored series, a timestamp, anything read from outside its own argument), the two calls could diverge — the error returned to `KonomiApp` would stop reliably matching the error actually applied to state, silently reintroducing the exact bug this fix closes (edit mode could close on what was actually an error, or vice versa). Flagged directly in a comment at the call site in `useKonomi.ts` so this dependency isn't invisible the next time someone touches `recommend`: keep it pure, or replace this shortcut with something that only computes the result once (e.g. dispatching a precomputed next-state rather than a bare action type).

**Where each retired `PanelToggleHeader`/`TagPoolRecommendationsPanel` piece ended up:** the Recommendations/Tag Pool toggle buttons and their `/` divider have no replacement (there's nothing left to toggle). `resultsHint` + Clear ✕ moved to a new `ResultsHeader.tsx`, rendered unconditionally above `RecommendationsBody` — no more tab-gating needed since there's only one surface. `TagIcon`+`LevelSelector` and `SortIcon`+`SortSelect` moved into `MixerBar`'s own header row first, then down again into `TagPoolBody`'s combined tabs+filters row once that header was removed — see below. The "drag or tap to load a slot" hint has no direct replacement either — the "+ Tag Pool" affordance's own always-visible label supersedes it.

### Level/Sort moved into the tabs row, and the header row that used to hold them is gone

The title/JP-subtitle/filled-count-badge row (browse and edit mode alike) and the Level/Sort filters row (edit mode only, right-aligned) both lived directly above the pool panel. Both removed — the count badge and title with no replacement, Level/Sort relocated into `TagPoolBody`'s own top row, inline with `SectionTabStrip`'s section tabs, rather than kept in a header row of their own.

**`TagPoolBody` now reads `level` via `useLevel()` directly, matching how it already read `sort` via `useSort()`** — the `level` prop is gone from `TagPoolBodyProps`. Only `onLevelChange` stays a prop: the read/write split this app already uses elsewhere (`MixerBar`'s own top comment used to document this same split for itself) — the setter still has to reach back into `KonomiApp`'s pruneTags cascade, so it can't just become a plain module-level read the way the value itself did.

**The combined row is `flex-col-reverse` + a single breakpoint switch to `flex-row`, not organic `flex-wrap`** — the same "hard breakpoint over independent reflow" call already made for `ResultsHeader`'s own two-group row (see "Divider and RECOMMEND-wrap thresholds" below for why that's the house style here). DOM order is `[tabs, filters]`; `flex-col-reverse` alone puts filters visually *above* tabs once stacked (filters is second in DOM, which col-reverse renders first), with no `order-*` utilities needed, while the wider `flex-row` tier reads that same DOM order left-to-right as-is (tabs left, filters right) for free. **Both wrappers need an explicit width once stacked, not just the tabs one** — confirmed live as a real bug in the first pass: `w-fit` on the filters wrapper (needed for its natural, right-aligned width in the inline/row tier) does nothing to constrain it in the *stacked/column* tier, since cross-axis sizing in a column flex container isn't clamped by the parent's width the way `min-w-0` clamps a row item along the main axis — there's no flex-shrink math on the cross axis at all. Left as `w-fit` unconditionally, the filters block rendered at its full unclamped content width and visibly bled past the card's right edge at narrow viewports instead of triggering `ScrollFadeArea`'s own scroll. Fixed with `w-full` below the breakpoint, `min-[Npx]:w-fit` only once inline.

**Both the tabs and the filters scroll horizontally now — this row is the one place in the bar besides the chip area where that's true.** Section tabs already did (`SectionTabStrip`'s own `ScrollFadeArea`); Level/Sort gained the same treatment when they lived in the old header row (wrap-then-scroll at the narrowest tier, reusing `ScrollFadeArea` the plain way `TagScrollArea` does — no tablist semantics, since these are two independent controls, not a tab set) and kept it moving down into this row unchanged.

**`chipAreaHeightPx` is now derived inside `TagPoolBody`, not passed in pre-computed from `MixerBar`.** `MixerBar` passes `poolPanelHeightPx` — the pool panel's *total* height budget (`effectiveHeightPx`) — and `TagPoolBody` measures its own combined row's rendered height via a `ResizeObserver` (the same live-measurement pattern `MixerBar`'s own `fixedOverheadPx` already established, for the identical reason: the old flat constant, `TABS_HEIGHT`, assumed the row was tabs-only and a fixed ~30px tall, but Level/Sort joining it means the real height now varies by breakpoint — one line inline, two stacked — so a hardcoded value would either overreserve or underreserve depending on which tier is active). `MixerBar` has no visibility into that row's real height anymore and doesn't need any: `CHIP_AREA_MIN` (the chip-area floor) moved into `TagPoolBody.tsx` alongside it, localizing the whole derivation to the one component that actually needs it.

**The custom direction-aware wheel/touch exemption for the filters' own scroll area became dead code once Level/Sort moved inside `dialogRef`'s subtree, and was deleted rather than re-plumbed.** Back when Level/Sort lived in the header row, they sat *outside* `dialogRef` (which wraps only the pool panel) — `MixerBar`'s `blockScrollThrough` handler (see "Nothing in this bar has a native scrollbar except the chip area" below) blanket-exempts everything inside `dialogRef` from its own `preventDefault`, but that filters area needed its own narrower, direction-aware exemption (checked `deltaX` vs `deltaY` for wheel, tracked touch-start position and locked an axis for touch) so a genuine horizontal scroll passed through while a vertical one still fell through to `preventDefault`, matching every other gesture on the bar. Now that Level/Sort live inside `TagPoolBody` — inside `dialogRef`'s subtree, like the chip area and `SectionTabStrip` always have — the existing blanket exemption already covers them correctly on its own: each `ScrollFadeArea` instance's own `overscroll-contain` (see "Tag Pool hierarchy" above) stops a gesture from chaining past its own scroll bounds once native scroll handles it, so there's nothing left for direction-aware JS to get right that the blanket exemption doesn't already get right for free — confirmed live (real trusted wheel events: a horizontal gesture over the filters moved `scrollLeft`, a vertical one left `window.scrollY` untouched) before deleting the custom logic, not assumed from the parallel to `SectionTabStrip` alone.

### The single box that grows: how edit mode actually expands

**Three architectures, in order, each rejected for a concrete reason found building the next:**

1. **`position: fixed`** (Step 1) — the bar pinned to the viewport bottom, browse-mode content given an explicit spacer (`MIXER_BAR_SPACER`, `pb-[290px]`, sized to the bar's own measured height) so nothing scrolled underneath it. Worked, but made "fit header+cards+mixer in one viewport" (the later `--result-card-height` clamp work, see "Recommendations layout" below) fight against a fixed element that never took part in normal document flow — the whole point of that feature is the page's own scroll behavior, which a fixed bar sits outside of by definition. Un-pinned back to normal flow once that requirement existed.
2. **Two separate boxes** (an overlay for the edit-mode content, sitting above the always-visible mixer card) — tried once the bar was back in normal flow and needed to visually "grow upward" without reflowing the page underneath it. Repeatedly produced a seam/notch/border-mismatch at the shared edge between the two boxes, through several different attempted patches (border-color matching, shadow clip-paths, negative-margin overlaps) — every fix treated the symptom (two independently-decorated boxes meeting) rather than the cause (there were two boxes at all).
3. **One box, `flex-col-reverse` + fixed height + `overflow: visible`** — an intermediate attempt at consolidating to a single element. Abandoned once it turned out to still leak the page's own `--bg` through a `clip-path` used for shadow trimming (`clip-path` clips backgrounds and content too, not just the shadow it was aimed at) — a real bug, not a dead end in the *structural* idea, but enough friction to reach for the simpler mechanism below instead.

**What actually shipped: one box (`cardRef`), a `marginTop` that goes negative in edit mode.** `cardRef` holds everything — the resize-handle row, the tag-pool dialog, the slots row, the controls row — as normal document-flow children, with exactly one border and one shadow drawn once around the whole thing (no shared edge to seam, because there's no second box). Growth happens via:

```
style={{ marginTop: editMode ? -(growableFixedOverheadPx + effectiveHeightPx) : 0 }}
```

`growableRef` wraps just the resize row + tag-pool dialog (the two rows that only exist/have height in edit mode) — nothing else. Algebraically, `cardRef`'s own rendered bottom edge is `naturalTop + marginTop + ownHeight`; since `ownHeight` grows by exactly `growableRef`'s own height when edit mode adds that content, the negative margin exactly cancels it out — the bottom edge (and everything below it: slots, controls) lands at the same page position whether edit mode is open or closed. This is the CSS-flow equivalent of what `position: fixed` gave for free, minus the reflow/viewport-fit conflict Step 1 hit.

**`growableRef` needs `flow-root`, not a plain `<div>`.** A plain wrapper lets its children's own top/bottom margins collapse *through* its boundary, under-measuring the true space they consume by exactly those margins — confirmed live as a real ~46px position-shift bug on opening edit mode (part of it; see the focus/scroll bug below for the rest). `flow-root` establishes a new block formatting context, containing the margins properly.

**Two distinct bugs, not one, produced that 46px shift; both had to be found and fixed.** After the margin-collapse fix above closed part of the gap, a real remainder stayed — traced to the browser's own default focus-scroll behavior: `dialogRef.current?.focus()` (see "Close behaviors" below) briefly renders the dialog partially above the viewport's top edge the instant it becomes visible, before the negative margin's paint has "caught up" — the browser doesn't know this is intentional, so it auto-scrolls the page to bring the newly-focused element into view, which reads as this whole bar visibly jumping on open. Fixed with `preventScroll: true` on both `.focus()` calls (open and close). Confirmed live via `getBoundingClientRect` diffed against the page (not the viewport) and `window.scrollY` before/after: slots/controls' own page position never actually changed — this was purely the browser's own focus-scroll, layered on top of the margin-collapse bug, not a second layout bug.

**`relative z-[var(--z-overlay)]` on `cardRef`.** Without an explicit `position` + `z-index`, this box is a plain static element — and a plain static element always paints *behind* any sibling with its own explicit stacking, regardless of DOM order (see "Z-index scale" above, which now documents this as a general rule). Confirmed live as a real bug once edit mode's growth visually overlapped the results grid above it: `ResultCard`'s front face (`position: absolute` + `z-raised`, for its own local flip-face stacking) painted *on top of* the expanded mixer. `z-overlay` is the same token the old `position: fixed` bar already used for its own page-level stacking — reused here, not a new one.

**The resize-drag "glitching," and the fix that generalizes:** see "This is the third time this bar has hit a variant of..." further below — `growableFixedOverheadPx`/`effectiveHeightPx`'s own split exists specifically so a `ResizeObserver`-measured value never gets combined with a synchronously-dragging one in the same commit.

**A related, separately-discovered bug in the same investigation: `SectionTabStrip`'s mount-time `scrollIntoView` scrolled the whole *page*, not just its own tab strip.** `TagPoolBody` (and the `SectionTabStrip` inside it) stays mounted at all times — see "State preservation" below — clipped to zero height via `max-h-0` when edit mode is closed, not unmounted. `SectionTabStrip`'s own effect (`tabRefs.current.get(activeKey)?.scrollIntoView({ ..., block: "nearest" })`) fires on every mount regardless, on the assumption that `block: "nearest"` can never affect the page's own scroll — true only while the strip is actually visible. Confirmed live as a real bug: with the strip clipped to zero height, there's no meaningfully scrollable block-axis ancestor nearby for `"nearest"` to satisfy, so the browser walks up to the *document itself* and scrolls the whole page to bring the (invisible, clipped) button into view — reproduced on every fresh page load. Fixed with a new `visible?: boolean` prop (default `true`, so no other caller needs to change) that gates the effect; `TagPoolBody` threads its own `editMode` prop through as `SectionTabStrip`'s `visible`. Confirmed live via a `scrollIntoView` interceptor with a full stack trace (not assumed from the symptom alone), and confirmed the intended in-panel behavior (bringing an off-screen tab into view via arrow-key nav) still works once the strip is actually visible.

### `position: sticky; bottom-[space-2xl]` — floats when the page scrolls, rests in flow otherwise

Requested explicitly as a replacement for plain normal flow: native browser behavior — pin to the viewport bottom once the page is tall enough to scroll, settle back into ordinary in-flow position (respecting `KonomiApp`'s own trailing `pb-[space-2xl]`) once everything already fits — rather than anything measured/computed in this file. `bottom-[var(--space-2xl)]`, not `bottom-0`: keeps the same minimum gap from the viewport edge the page already guarantees on the left/right (`KonomiApp`'s own `px-[space-2xl]`), so the frame reads as one consistent gutter on every side regardless of which mode the bar is in.

**Investigated live before adopting, three specific risks, all confirmed clear:**

1. **The static-vs-positioned trap** (see `z-[var(--z-overlay)]`'s own comment, above) doesn't reopen — `sticky` is a *positioned* value exactly like `relative` was, so it satisfies the same "must be positioned for an explicit z-index to out-rank a sibling's" requirement that fix already established. Confirmed live: a hit-test at the exact point the grown panel visually overlaps content above it still resolved to this bar's own element, not whatever's behind it.
2. **`KonomiApp`'s own `overflow-x-clip` does *not* hijack the sticky containing block.** Any non-`visible` overflow value technically makes a box a "scroll container" per spec, which raised a real question: does `position: sticky` here resolve against the true viewport, or against that div's own box? Tested with a genuinely tall page (a 2000px spacer): the bar stuck to the real viewport bottom for the entire scroll range and returned to normal flow only once the page ran out — confirmed the true viewport, not the ancestor.
3. **The resize-drag still behaves correctly while stuck.** Dragged the handle up 150px in 30px increments: the bar's bottom edge stayed pinned to the viewport on every single frame, and the panel's height grew in exact 1:1 lockstep with the drag delta, both directions. `handleMove`'s own math (tracking `clientY` deltas in viewport coordinates) is already indifferent to which positioning scheme the box uses.

**`marginTop` (see its own comment, above) stays exactly as it was — computed unconditionally, whether the bar happens to be stuck or not — and that's deliberate, not an oversight.** While genuinely stuck, it's confirmed to be a pure no-op for the bar's *final rendered position*: native `sticky`'s own `bottom` offset determines that regardless of what `marginTop` says (verified live by forcing `marginTop: 0` while stuck and diffing the result — byte-identical to the unforced version). It's tempting to read that as "so skip computing it while stuck" — **this was tried and reverted; see the seventh trap instance below for exactly why.**

### A seventh trap instance, same mount-gating/circular-dependency family as the six above — this one doesn't oscillate or get stuck open, it feeds back into the very thing it measures

`marginTop` has a second job beyond repositioning the box, one easy to miss because it's invisible while stuck: it also cancels the growable content's contribution to the *page's own total layout height* (`position: sticky` does not remove a box from normal flow — only *where it paints* changes, not how much vertical space it's allocated for layout/`scrollHeight` purposes). An attempt to make the "no-op while genuinely stuck" explicit — an `isStuck` state, computed from remaining scroll distance (`document.documentElement.scrollHeight - scrollY - innerHeight`), gating `marginTop` to `0` whenever true — broke this second job: with `marginTop` zeroed, the growable content's real height leaked straight into the page's own `scrollHeight`, which is the exact input `isStuck`'s own formula reads. Opening edit mode could push a bar that was *not* stuck a moment ago over the sticky threshold, purely as a side effect of the un-compensated growth — flipping `isStuck` true (or leaving a stale value) as a consequence of the very change its own value was supposed to gate.

Confirmed live as a real, reproducible, *worsening* regression, not just a theoretical loop: the bar's bottom edge visibly pushed *down* on open instead of the box growing purely upward, and repeated open/close cycles while stuck compounded the drift further each time rather than settling — matching a report of "works fine right after a hard refresh, breaks after cycling through sticky-mode edits a few times." Reverted in favor of leaving `marginTop` unconditional, exactly as it was before sticky existed — a confirmed no-op purely visually whenever the bar happens to be stuck, at the cost of one redundant (harmless) style computation in that case. **A much better trade than a value that can feed back into its own input** — the generalized tell, extending the family above: before gating any value on "is X currently true," check not just whether X's own measurement could later be fed by something that value goes on to affect (the sixth instance's flavor), but whether the thing you're about to stop computing has a *second*, less obvious job the first job's absence would quietly break.

**A related debugging note, worth recording so it isn't rediscovered the hard way: a since-resolved stutter reported during this same investigation traced to stale browser/GPU-process state, not a code bug.** Reported as visible only in sticky mode, reproducible on the reporter's own machine but not via any fresh-process Playwright test (position/frame-geometry sampling, `Performance.getMetrics` layout/style-recalc counts, `sharp`-based screenshot pixel-diffing, and `LayerTree` compositing events were all tried, and all came back clean or identical between sticky and non-sticky). A tab hard-refresh didn't fix it; a full browser **process** restart did. That combination — not reproducible from a fresh process, survives a page reload, cleared by fully restarting the browser — points at accumulated compositor/GPU-process state (plausibly destabilized by this same investigation's own rapid Fast-Refresh churn on a layout-affecting component mid-session) rather than anything in `MixerBar.tsx`/`TagPoolBody.tsx`. Worth checking for this signature specifically before assuming a visual glitch is a code bug: if a fresh browser *process* (not just a fresh tab/reload) makes it disappear, it probably isn't one.

### State preservation: the pool panel is always mounted, never remounted

The pool panel (row 1) is toggled via `max-h-0 overflow-hidden` keyed off `editMode`, not conditional JSX — the exact same trick the retired `TagPoolRecommendationsPanel` used for tab-switching (see "Tag Pool and Recommendations became two tabs" above), generalized from two tab keys to one boolean. This is required, not stylistic: `TagPoolBody`'s own `activeSectionKey` state and every `ScrollFadeArea` scroll position inside it have no persistence outside the live DOM, so unmounting this subtree on every close would reset both, every time. `max-h-0 overflow-hidden` (rather than `hidden`/`display:none`) was the specific choice here: the subtree still lays out normally underneath the clip, so `ScrollFadeArea`'s `scrollHeight`/`clientHeight` measurements stay correct the whole time, with no one-frame `ResizeObserver` catch-up delay on reopen the way a `display:none`→visible transition can have.

### Nothing in this bar has a native scrollbar except the chip area — title, slots, and controls are fixed by construction, not by a scroll fallback

An earlier version gave the bar's own outer container `max-h-[100dvh] overflow-y-auto` in edit mode, letting the whole bar scroll internally on short viewports as a safety net. **This was replaced entirely** — the outer container now carries no scroll/overflow behavior in either mode, and the pool panel wrapper (see below) has no scrollbar of its own either. Two reasons: first, an internal scroll on the bar defaults to `scrollTop: 0`, meaning an overflow would show the *top* (title/slots) and hide the *bottom* (the controls row) until manually scrolled down — backwards from the actual requirement, which is that the controls row must always be reachable, unconditionally. Second, and more fundamentally: title, slots, and controls must **never** scroll, resize, or move, full stop — not "usually don't, thanks to a generous cap," an exact guarantee. That guarantee now comes from clamp math instead of a scroll fallback: the pool panel — the only part of this bar that ever changes size — is bounded so that `(fixed rows) + (pool panel)` can never exceed the viewport in the first place, so there's never a scenario where the outer container would have needed to scroll. See `clampPoolPanelHeight` below.

The only *vertical* scrolling anywhere in this bar is `TagPoolBody`'s own existing chip-area `ScrollFadeArea` (fade gradients, hover arrows, press-and-hold — all unchanged, see "Tag Pool hierarchy" above). Its combined tabs+filters row above the chip area does scroll — horizontally, both the section tabs and the Level/Sort filters, each independently — see "Level/Sort moved into the tabs row" below; that row is still sized to its own natural content (or its own live-measured height, once Level/Sort joined it — see that section), never vertically clipped or resized the way the chip area is.

### Pool panel height: exact, not a cap — 50% of viewport on first open, drag-resizable well past that, persisted

The pool panel does not hug or cap to content — it is **exactly** `effectiveHeightPx` tall, regardless of which section tab is active or how much content that section has. Switching from a long section (e.g. Theme, Otaku level) to a short one (Genres) leaves visible empty space below the shorter section's chips rather than shrinking the panel — confirmed live, panel height measured byte-identical across a tab switch between the two. Only the resize handle (or the very first default) may change this value.

**The resize handle lives at the very top of the edit surface** — not between the slots and the pool panel, where an earlier version placed it. Dragging it only ever visibly resizes the pool panel (title/slots/controls are fixed), but positioning it at the top matches the more natural mental model — "pull this to make the whole panel bigger" — even though mechanically it's still just the one flexible region responding. **Usable at every breakpoint, not desktop-only** — an earlier version hid it below the same 993px tier the controls-row divider uses (mouse/pointer-only, no touch handlers), leaving mobile with no way to resize at all; that gate is gone.

`handleResizeStart` is now Pointer Events (`onPointerDown` + `setPointerCapture`), not the dual mouse/touch listener pairing (`onMouseDown`/`onTouchStart`, then `mousemove`/`touchmove`+`mouseup`/`touchend` on `window`) it used before — that pairing mirrored `ScrollFadeArea`'s own press-and-hold arrows deliberately, to avoid introducing a second interaction pattern for just this one control (that reasoning still holds for `ScrollFadeArea`'s arrows themselves — press-and-hold buttons, not a free vertical drag across the whole viewport, so they don't carry the same risk this control does). Switched here specifically for the capture guarantee: `setPointerCapture` routes every subsequent `pointermove`/`pointerup` for that pointer id straight to the grip, regardless of where the finger/cursor physically travels, and tells the browser this element now owns the gesture — confirmed live (real, trusted mouse-driven events; `hasPointerCapture` reports `true` from the first `pointermove` onward) that capture engages correctly. `touch-action: none` (`touch-none` in the className) and an explicit `preventDefault()` on every `pointermove` are both still kept alongside it, not replaced by it — capture guarantees *where* events go, not that the browser won't independently start its own scroll gesture for a pointer it doesn't yet consider captured, so this is three overlapping defenses for one requirement ("a drag on this handle must never scroll the page behind it"), not three redundant ones. No keyboard equivalent yet — an accepted gap, not solved in this pass, same spirit as the no-focus-trap gap above.

**On first open (no persisted value yet), the default is exactly 50% of the viewport height** — read once via `useDefaultPoolPanelHeight()` (`tagPoolPrefs.ts`), not re-derived on every render. Deliberately *not* live-recomputed on every render: continuously tracking `window.innerHeight` would make the panel silently change size mid-session if the browser window resized before the user ever dragged, contradicting "only the handle changes this." The chosen height persists via the exact same `useSyncExternalStore` + `localStorage` pattern `tagPoolPrefs.ts` already uses for level/sort — `usePoolPanelHeight()`/`setPoolPanelHeightPref()`, no new persistence mechanism. `null` means "never dragged this session, use the 50%-of-viewport default"; once the user drags, a stored pixel value exists and wins from then on.

**Three real bugs surfaced getting this right, in sequence, each masking the next.** First: `clampPoolPanelHeight` (used directly in `MixerBar`'s render body, not only through `usePoolPanelHeight`'s SSR-safe `useSyncExternalStore` path) read `window.innerHeight` completely unguarded — a hard SSR crash (`Error: window is not defined`), not a warning, since `MixerBar` renders server-side too and `window` doesn't exist there. Fixed with a `typeof window === "undefined"` guard, falling back to `Math.max(px, POOL_HEIGHT_MIN)` (no upper clamp) when there's no viewport to clamp against. That fix uncovered the second bug, previously invisible behind the crash: the *default height itself* was a plain `useState(() => window.innerHeight * 0.5)` lazy initializer, guarded the same way — but "guarded against crashing" and "guarded against a hydration mismatch" aren't the same thing. The server has no `window` (falls back to a placeholder), while the client's own *first* render already has a real one and would compute the actual value immediately — two different numbers for the same inline `style={{height}}` attribute (on `TagPoolBody`'s chip-area `ScrollFadeArea`), which React's hydration flags as a mismatch even though that attribute sits inside a visually-collapsed `max-h-0 overflow-hidden` wrapper the whole time — **being invisible doesn't exempt an element's attributes from the server/client comparison**, confirmed live via the exact warning (`style={{height:365}}` vs `style={{height:"60px"}}`) once the crash stopped hiding it. A `useState` + `useEffect(() => setState(...), [])` pair (correct the value right after mount) was the first fix attempted for *this* — rejected by this project's own lint config (`react-hooks/set-state-in-effect`) for the same reason that rule exists generally: it causes an avoidable extra cascading render on every mount. The fix that stuck: `useDefaultPoolPanelHeight()`, a `useSyncExternalStore` hook whose `getServerSnapshot` argument returns `POOL_HEIGHT_MIN` and whose subscribe function never calls its callback (there's nothing to subscribe to — this is a one-time "what's the viewport right now" read, not a live value) — React guarantees the client's first render matches whatever `getServerSnapshot` returned, with the real client value only appearing in a separate, ordinary, warning-free re-render immediately after.

A **third bug, found later during a proactive sweep for exactly this class of problem**, was hiding behind the same crash-guard on `clampPoolPanelHeight`'s *other* argument. The `typeof window === "undefined"` guard stopped the crash, but its real branch still read `window.innerHeight` inline, immediately, on the client's first render — the same crash-safe-but-not-hydration-safe gap as the default-height bug above, just on the ceiling instead of the seed value. The server always took the fallback (no upper clamp), while the client's first render took the real, viewport-dependent ceiling — two different answers for the same input whenever that ceiling would actually pull the value down (a short viewport). This one stayed invisible longer than the first two because `CHIP_AREA_MIN`'s own floor happened to absorb the entire gap before it reached anything actually rendered — confirmed live at a 400px-tall viewport, no visible mismatch — but that was incidental to those specific constants, not a real guarantee; retuning `POOL_HEIGHT_MIN`/`FILTERS_AND_TABS_HEIGHT`/`CHIP_AREA_MIN`/`EDIT_MODE_FIXED_ROWS_HEIGHT` later could have silently reopened a visible one. Fixed the same way as the default height: `clampPoolPanelHeight` is now a pure `(px, max) => number` function with zero `window` access, and the viewport ceiling moved into its own `usePoolPanelMaxHeight()` hook (`tagPoolPrefs.ts`) — same `useSyncExternalStore` pattern, `getServerSnapshot` returning `Number.POSITIVE_INFINITY` (safe because the only value ever clamped against it pre-hydration is `POOL_HEIGHT_MIN` itself, which trivially satisfies "no ceiling" either way). `MixerBar` reads this hook alongside `useDefaultPoolPanelHeight()` and threads it into both the render-time `effectiveHeightPx` computation and the live-drag `handleMove` clamp. Verified live at a 1400×400 viewport (forces the real ceiling below `POOL_HEIGHT_MIN`): zero console warnings, and a drag-to-extreme correctly clamped the persisted value to exactly `400 − 345 = 55`, confirming the drag handler uses the live post-hydration max rather than a stale `Infinity`. The general lesson, worth remembering next time a value is derived from `window` anywhere in this render tree: a `typeof window === "undefined"` guard only proves the code won't crash server-side — it says nothing about whether the client's *first* render matches what the server actually sent, which is the real hydration contract. `useSyncExternalStore` + `getServerSnapshot` is the only mechanism in this codebase that gives that guarantee; reach for it (not a guard, not `useState`+`useEffect`) any time a render body needs to read `window`/`document` directly.

**The clamp bound is exact (`viewport height − EDIT_MODE_FIXED_ROWS_HEIGHT`), not a rough fraction of the viewport.** This is the app's first persisted *raw pixel value* rather than a token/enum (level/sort/section are all discrete), and the very first version clamped it to a flat 75%-of-viewport fraction — which was not precise enough once the outer-scroll safety net was removed: a generous 75% could still allow a drag that pushes the fixed rows below the fold on a short viewport. `EDIT_MODE_FIXED_ROWS_HEIGHT` (345, `tagPoolPrefs.ts`) is the actual measured combined height of everything in the bar that isn't the pool panel — resize handle, title, slots, controls, padding, gaps — measured live at the narrowest (390px, mobile) width, where the controls row wraps to 2 lines and this is tallest (341.5px measured, 345 leaves a small buffer; desktop measures a shorter 256.5px, so this is intentionally conservative there rather than pixel-precise — the same flat-conservative-constant tradeoff `--masthead-height`/`--mixer-bar-height` now make in `globals.css`'s own `--result-card-height` clamp, see "Recommendations layout" below). `clampPoolPanelHeight(px, max)` applies this bound uniformly — to the default, to a persisted read, and to a live drag alike — one clamp, not "clamp the persisted value on read, then separately clamp drags," so `(fixed rows) + (pool panel)` never exceeds the viewport regardless of where the number came from. `max` itself comes from `usePoolPanelMaxHeight()` (see above) rather than being computed inline, so this function has no `window` access of its own — it's a plain, pure `(px, max) => number`. Confirmed live: dragging the handle 350px past the starting height clamped exactly at `viewport − 345`, not a px further.

**The dragged/default value is reduced by the combined tabs+filters row's own height before it reaches the chip area, so the panel's *total* rendered height matches what the user actually dragged to** — rather than the chip area alone matching it with that row added on top. This used to be a flat constant (`FILTERS_AND_TABS_HEIGHT`/`TABS_HEIGHT`, `MixerBar.tsx`) subtracted in `MixerBar` itself; it's now a live `ResizeObserver` measurement taken inside `TagPoolBody`, since Level/Sort joining that row made its real height vary by breakpoint instead of staying a flat ~30-42px — see "Level/Sort moved into the tabs row" above for the current mechanism and why the flat-constant approach stopped being enough.

**A real, non-obvious CSS discovery while building this: `overflow: hidden` on a `flex-col` container whose explicit height is *smaller* than its content clips from the start (top), not the end (bottom).** The first version gave the pool-panel wrapper both an explicit `height: effectiveHeightPx` and `overflow-hidden`, intending it as a defensive clip in case the tabs+filters row's estimated height ever ran long. Confirmed live via `getBoundingClientRect()`: the row measured *above* its own parent's top edge once clipped (`overflow: visible` on the same element immediately snapped it back to matching the parent's top exactly) — meaning the browser was clipping the *tabs+filters row* from view while keeping the *chip area* fully intact, exactly backwards from the goal (tabs/filters should always stay visible; the chip area is the one part that should ever be visually truncated). The fix: no explicit height and no `overflow-hidden` on this wrapper at all — its natural height is just the tabs+filters row + `TagPoolBody`'s own rendered height, which already sums to `effectiveHeightPx` by construction now that `chipAreaHeightPx` is pre-reduced by that row's own live-measured height (see above).

**Passing a live pixel value through to `ScrollFadeArea` needed a real prop addition, not a computed class.** `ScrollFadeArea`'s existing `height` prop is a static Tailwind class string; a class built from a runtime pixel number would hit the exact bug "Runtime-computed dimensions" (above) describes. `ScrollFadeArea` gained a `heightPx?: number` prop instead — a *fixed* height (not a max-height/cap), matching the "never hugs" requirement above: when set, it renders an inline `style={{ height: heightPx }}` and omits the `height` class entirely, otherwise behaving exactly as before. `TagPoolBody` threads this through as `chipAreaHeightPx`, undefined only pre-hydration.

**A value derived from an element's own presence can't also gate that element's presence without a settle step, or it oscillates.** Found when the resize-handle row (and its 50%/100%/reset shortcuts) was made to hide itself once `poolPanelMaxHeight` drops so low that nothing the row offers can do anything clampPoolPanelHeight wasn't already forcing on its own. `poolPanelMaxHeight` comes from `fixedOverheadPx`, a `ResizeObserver` reading `bar`'s and `dialog`'s *current* rendered rects — which include the resize-handle row's own height only while it's mounted. Gating the row's mount directly on the live `poolPanelMaxHeight > POOL_HEIGHT_MIN` comparison is a feedback loop: hiding the row shrinks the measured overhead, which raises the ceiling back above the threshold, which re-mounts the row, which re-measures the larger overhead and hides it again — confirmed live as a real, visible flicker sitting exactly at the boundary. The fix: settle the decision in its own `useState` rather than reading the live comparison inline, judging each candidate against "what the ceiling would be if the row were shown" (adding the row's own fixed height back on top of the measurement whenever it's currently hidden) instead of whatever the measurement happens to read right after the row's last mount-state flip. Same family as the hydration bugs above — a value can be correctly derived and still be wrong the moment it also controls the presence of the thing it was derived from. Worth checking for again any time a future `ResizeObserver`/live-measurement value feeds a mount/show-hide decision in this bar.

**The trap has a subtler variant: the input number can look completely stable and still be the loop, because what's circular is its *meaning*, not its value.** Found again in `TagPoolBody`'s combined tabs+filters row (see "Level/Sort moved into the tabs row" above), deciding whether filters show full labels or icon-only. The first fix attempt reconstructed "filters' width with labels shown/hidden" from one live measurement (`filtersScrollWidth`, the filters' own `ScrollFadeArea` `onMeasure`) via a ternary keyed off the very `filtersCompact` state being decided — reasoned through carefully twice, on the assumption that reconstructing-from-a-live-value (rather than reading a raw comparison) was itself the fix, the same shape that closed the resize-handle-row loop above. It still crashed live (`Too many re-renders`, `TagPoolBody`). A value trace caught what reasoning missed twice: `filtersScrollWidth` stayed frozen at 482 (the full-label width, from before the loop even started) across the *entire* loop, while `filtersCompact` kept flipping — because React can flip a settled decision many times in one synchronous pass, faster than the browser can lay out the DOM and fire a fresh `ResizeObserver` measurement. Each flip re-interpreted that same frozen 482 as meaning something different — once "this **is** the icon-only width," once "this **is** the full-label width" — a decision reading a measured width of the thing it's deciding, just with the circularity hidden in the *interpretation* of a number that never itself changed, rather than in the number changing. The fix: stop reading the filters' width live at all. `FILTERS_ICON_ONLY_WIDTH_PX` (`TagPoolBody.tsx`) is now a hardcoded, measured-once constant, same treatment as `LABEL_DELTA_PX` beside it — both decisions (icon-collapse, stacking) are pure functions of `rowWidthPx`/`tabsScrollWidth` (genuinely independent of the decisions) and these two fixed constants, never of anything the filters' own render state affects. **The generalized tell, for next time: a decision may not read *any* measured value whose interpretation depends on the decision's own current state — check not just "does this value change when the decision changes" but "does what this value *means* change when the decision changes." A frozen number can still fail the second test.**

**A third instance of the same family, found later, in a different shape: not a mount/show-hide loop, but a straightforward render-timing race between a synchronous, per-frame value and an async `ResizeObserver` measurement.** The pool panel's growth in edit mode is driven by a single `marginTop`, computed as `-(growableFixedOverheadPx + effectiveHeightPx)` (`MixerBar.tsx`) — `effectiveHeightPx` updates synchronously on every `mousemove` tick while dragging the resize handle, but `growableFixedOverheadPx` (the rest of the growable content's own height) only updates whenever its `ResizeObserver` callback happens to fire, which lands in a different frame than the drag's own state update. Reading both from one blended live measurement made the bar visibly jump/lag on every drag tick, since the two values weren't guaranteed to land in the same commit. The fix: split the measured quantity into the fast-changing part that's already available synchronously (`effectiveHeightPx`, driven directly by the drag) and the slow-changing part that's safe to measure asynchronously (`growableFixedOverheadPx = growableRef`'s measured height minus `effectiveHeightPx`, which stays constant *during* a drag since both terms move together) — never let the `ResizeObserver`-driven half of a computed value change on the same tick a synchronous gesture is also changing it.

**This is the third time this bar has hit a variant of "don't let an async/derived measurement drive a value that's also changing synchronously, right now" (see the mount-gating loop and the frozen-meaning loop above) — worth treating as a standing rule rather than three unrelated bugs: whenever a `ResizeObserver`/live-measurement value feeds anything that also updates synchronously within the same interaction (a drag, a keystroke, anything per-frame), split it into its synchronous-safe and observer-safe parts *before* combining them, rather than reading one blended live number. Check for this any time a fast, continuous gesture (not just a mount/unmount decision) sits anywhere near a `ResizeObserver`-fed value.**

**A fourth instance, same family, different sub-rule: `fixedOverheadPx` and `growableFixedOverheadPx` (both above) were themselves each measured in a plain `useEffect`, which runs *after* the browser paints — so on the very first `editMode` open per page load, one real frame painted using the stale bootstrap/zero value before the correction landed, and `cardRef`'s negative-`marginTop` compensation was wrong for that frame: the whole bar visibly jumped down by the resize row's height, then snapped back up once the effect fired. Confirmed live via frame-by-frame `getBoundingClientRect()` sampling (Playwright, `requestAnimationFrame`-gated): the controls row's `top` read one wrong value on the first sampled frame after opening, then held the correct value for every frame after — reproduced identically on mobile and desktop, gone entirely on the second open in the same session (state had already settled from the first). The fix: both measurement effects (and the `effectiveHeightPxRef` mirror that feeds the growable one) are now `useLayoutEffect`, not `useEffect` — it runs synchronously after the DOM mutation but *before* the browser paints, so the correction lands in the same commit the open itself does, and no wrong frame ever reaches the screen. This is the second documented instance of this exact sub-rule — `ResultCard`'s hint-wrap alignment (see "The icon buttons themselves must never resize or reposition when the hint mounts," above) hit it first, for the identical reason, with the identical fix. **Worth stating as its own standing rule, alongside the sync-vs-async-value one above but distinct from it: that one is about *what* a value is computed from (never blend a synchronous per-frame value with an async observer-fed one); this one is about *when* a measure-and-correct effect runs (if it reads layout and writes state that changes layout, it must be `useLayoutEffect`, or a wrong frame paints first, every single time that measurement needs to newly resolve — not just during a fast gesture, but on any transition, including a one-time mount).**

**A fifth instance, back in the sync-vs-async-value family (not the `useLayoutEffect` one) — same rule, a trigger that isn't a `ResizeObserver` at all.** `poolPanelMaxHeight` (`usePoolPanelMaxHeight`, `tagPoolPrefs.ts`) is a `useSyncExternalStore` hook that subscribes to `window`'s own `resize` event directly and independently of anything in `MixerBar` — freezing `fixedOverheadPx` (this hook's own input) during a drag, as the fourth instance above already does, doesn't stop *this* hook from still returning a fresh, live value on every `resize` event regardless, since it reads `window.innerHeight` itself rather than only reacting to its `fixedOverheadPx` argument changing. The render body's own `effectiveHeightPx = clampPoolPanelHeight(dragHeightPx ?? …, poolPanelMaxHeight)` re-clamped `dragHeightPx` against this live ceiling on *every* render — and mobile browsers resize the visual viewport (firing a real `resize` event) when their address bar/toolbar hides or shows, which commonly happens mid-touch, i.e. exactly while a user is dragging this handle. Confirmed live: dragged the panel to 413px, simulated a viewport shrink mid-drag (`page.setViewportSize`, standing in for the address bar showing), and the panel snapped to 341px instantly, pointer still down, zero finger movement. `handleMove` (the drag's own per-tick handler) already clamps against `poolPanelMaxHeight` as it stood at drag-*start* — a plain closure variable, frozen for the gesture's whole duration by construction, never re-read — so `dragHeightPx` arriving at the render body was already correctly bounded; the fix was to stop re-clamping it a second time there against whatever the *live* ceiling happens to read on that render, trusting the value handleMove already produced instead (persisted/default values still get the live clamp, unchanged — only the actively-dragging case skips it). Same standing rule as above, restated for this trigger: **a value that's already been correctly bounded against a *frozen* snapshot of a live measurement must not be re-bounded against that same measurement's *current* value on every subsequent render — re-clamping is not idempotent once the ceiling itself can move mid-gesture.**

**A sixth instance, back in the mount-gating family (the very first entry above, "a value derived from an element's own presence can't also gate that element's presence") — except this time the loop doesn't oscillate, it gets stuck open forever.** `canShowResizeHandleRow` (`poolPanelMaxHeight > POOL_HEIGHT_MIN`) gates whether the grip — and the `pointerdown`/`setPointerCapture` it owns — is even mounted. That's a live value, reactive to the exact same `resize` event that can fire mid-drag (the fifth instance's own address-bar/window-resize trigger). Reproduced live: started a drag, shrank the viewport mid-gesture until this flipped false, released the pointer into the void — the grip had already unmounted, taking its own `pointermove`/`pointerup`/`pointercancel` listeners with it (they were attached to the grip itself at the time), so `handleEnd` never ran. `isDraggingRef`/`dragHeightPx` stayed stuck at their mid-drag values *permanently* — not just for that render, but for the rest of the component's lifetime, since nothing was left to ever call `handleEnd` again. Confirmed live this was the shared root cause behind three symptoms that looked unrelated when first reported: a drag that "keeps going" after release, the resize controls disappearing for good, and a *later* reopen showing a stale height/position left over from a since-changed viewport — all three were just different downstream faces of `fixedOverheadPx`'s measurement effect (fourth instance, above) being permanently frozen by a `isDraggingRef` that could no longer ever unset itself.

Two-part fix, addressing both the trigger and the consequence, since neither alone fully closes this: (1) mounting the grip for a drag's whole duration regardless of what the live ceiling does mid-gesture (superseded since — see below — by the broader `isRowInteractionActive`, but originally a narrower `isDragging`, real `useState` not just `isDraggingRef`, specifically because this project's own lint rules correctly reject reading a ref's `.current` during render). (2) Even so, that mount condition can't cover *every* path that removes the grip — `editMode` itself can still close mid-drag via Esc/click-outside, independent of anything this control does — so `handleResizeStart`'s own `pointermove`/`pointerup`/`pointercancel` listeners moved from the captured grip element onto `window`. `setPointerCapture` still lives on the grip (it governs gesture *ownership*/hit-testing, not which element is allowed to observe the resulting events) — `window` always receives these events regardless of which element currently holds capture, so the drag can now always cleanly end even if every single element it started on has since been removed. **The generalized tell: whenever a gesture's own start and end are wired to the same DOM node (attach-on-start, detach-on-end), check whether anything else in the render tree can make that specific node unmount *while the gesture is still in progress* — if so, the end-handler's cleanup needs a home that survives the node's removal, not just a mount condition that tries to prevent it.**

**The fix above was itself incomplete — confirmed live on a real iPhone, reported as buttons "not functioning or triggering some other type of button."** `canShowResizeHandleRowDisplay` only ever protected the grip's own mount. The 50%/100%/Reset shortcut buttons *beside* it are each individually gated on the exact same live ceiling (`canReachHalfHeight`/`isAtHalfHeight`/`canReachFullHeight`/`isAtFullHeight`, all `poolPanelMaxHeight`-derived) — and pressing one of *them* isn't a drag at all, so the original `isDragging`-based protection never covered them. Reproduced directly: pressed the Reset button, forced a viewport-height change mid-press (exactly what an iPhone's Safari address bar does during active scrolling/touch), the ceiling crossed its threshold, and Reset unmounted while the finger was still down on it — whatever now sits at that same screen point (confirmed live: the bar's own outer card) is what a real release activates instead, reading as an unrelated button firing.

**Generalized the fix rather than special-casing a fourth button:** `isRowInteractionActive`, one shared plain boolean, `true` on `pointerdown` and `false` on `window`-level `pointerup`/`pointercancel` only — never derived from `poolPanelMaxHeight`, `scrollHeight`, or any other live value, which would just reintroduce the seventh trap instance's own shape in a new guise (see "`position: sticky`" above): the entire point is to *freeze* the mounted set at whatever it already was when the press started, not keep re-deriving it from the value the press is trying to outlast. Attached once, via `onPointerDown` on the container both the grip and the three shortcut buttons already share as a common ancestor — a single listener there catches a press starting on any of the four through normal bubbling, rather than repeating the wiring four times. `canShowResizeHandleRowDisplay` and each of the three buttons' own conditions all became `isRowInteractionActive || (existing live condition)`. `isDragging` (the narrower, grip-only `useState`) had no remaining reader once this landed and was removed outright — `isDraggingRef` stays, since it still separately does its own job of freezing `fixedOverheadPx` during an actual height-changing drag specifically (a tap on the other three buttons was never a drag, and never needed to freeze that).

**That generalized fix was itself wrong, confirmed live on a real iPhone and reproduced directly via Playwright — a genuinely new failure mode, not the same bug recurring: pressing any *one* of the four elements revealed *all four*, including ones that were never reachable at that size.** Reported as "when i click on the drag or arrow then it shows all the other arrow icon affordances." Root cause: `isRowInteractionActive` was a *single* shared boolean OR'd uniformly into all four independent conditions — `X || true` is `true` regardless of what `X` was, so the instant *any* press started, every one of the four conditions evaluated to `true` simultaneously, whether or not that specific element had ever been reachable. Confirmed directly: at a viewport where the panel sat at its default height (`Reset` correctly not yet mounted, count 0), dispatching only a `pointerdown` on the grip — no move, no release — made `Reset` appear (count 1). A shared flag can distinguish "an interaction is in progress" from "no interaction," but it cannot distinguish *which* element that interaction was for — the previous fix conflated "keep the thing being pressed from unmounting" with "reveal the whole row," and only the first was ever the actual goal.

The fix: replace the one shared boolean with `frozenReachability`, a snapshot *object* — `{ canShowRow, canReachHalf, canReachFull }` — populated from the three live, `poolPanelMaxHeight`-derived values at the exact instant `handleRowPointerDown` fires, and cleared to `null` on the same `window`-level `pointerup`/`pointercancel` as before. Each of the four conditions now *substitutes* its own frozen field in place of the live one (`frozenReachability ? frozenReachability.canReachHalf : canReachHalfHeight`) rather than OR-ing a shared flag in — a per-element replace, not a row-wide reveal. Critically, this snapshot covers only the *reachability* half of each condition (whether the ceiling makes an element reachable *at all*, which should never change mid-press for reasons outside the user's own gesture — a mobile address-bar resize, not a drag). The *current-height* half (`isAtHalfHeight`/`isAtFullHeight`/`isAtDefaultHeight`, all compared against the live, actively-dragged `effectiveHeightPx`) is deliberately left untouched and fully reactive — freezing those too would have silently broken the legitimate, wanted behavior where a shortcut button hides itself the instant a real drag actually reaches that exact height. **The generalized tell, sharpening the sixth trap instance's own lesson: when several independent elements share one "freeze this during a press" mechanism, freezing must be per-element, not per-row — a single shared boolean can protect against the wrong kind of change (an unwanted unmount) while accidentally causing a different wrong kind of change (an unwanted reveal), because OR-ing one flag into N independent conditions makes all N of them true together the moment any single one of them would have been.** Verified via Playwright along all four angles this fix touches: (1) pressing a visible element does not reveal an unrelated, legitimately-hidden sibling; (2) a button that *is* visible still survives a live ceiling shrink mid-press (the original bug this whole mechanism exists to fix, re-confirmed still fixed); (3) the exact narrow-viewport shape from the user's own screenshots (grip shown, 50% hidden, 100% shown) — pressing only the grip no longer reveals the hidden 50% button; (4) live "at height" feedback during a real drag/click still works (the 100% button correctly hides once actually at 100%).

**A second, unrelated bug found investigating the same report: `setPointerCapture` can throw** (`InvalidPointerId`) under rapid/overlapping touch conditions — a fast, repeated series of taps can mean the specific pointer id `handleResizeStart` receives is no longer considered active by the time the call runs. Uncaught, that exception aborted the *rest* of the function too, silently: `isDraggingRef` never got set and the drag-continuation listeners never attached. Wrapped in a plain `try`/`catch` — a failed capture only loses the gesture-ownership guarantee for that one interaction (see the resize-handle section above); the drag itself still starts and tracks correctly via the `window`-level listeners regardless. **Worth remembering generally: any DOM API called inside a React event handler that *can* throw under real (not just malformed-test) conditions should be assumed to eventually do so on mobile under fast, repeated input — an uncaught throw there doesn't just fail that one call, it silently skips everything else the handler was supposed to do.**

### The 50%/100%/Reset shortcut buttons are `min-[993px]`-only now — requested directly, not a bug fix

A touch-primary user already has the grip itself for manual resizing, full-range and one gesture away — the three shortcut buttons (jump to 50%/100%/default) are a mouse-driven, click-based convenience desktop keeps, not something mobile needs alongside the grip. Removed from mobile on request via `hidden min-[993px]:flex` on the buttons' own wrapping `<div>` — nothing else changed.

`min-[993px]` isn't a new number invented for this: it's this exact row's own prior desktop threshold (an earlier version hid the *entire* resize row — grip included — below 993px, reverted at the time because it left mobile with no way to resize at all; this is deliberately narrower, hiding only the three shortcuts and never the grip) and the same breakpoint Row 3 below already uses for its own icon-vs-text desktop split (`min-[993px]:hidden` on Tag Pool/Random/Clear's mobile icon-only form) — one consistent "is this desktop" line for the whole bar, not a second one invented here.

**Purely a rendering change, nothing underneath it removed or altered.** Every fix from the two entries above — `frozenReachability`'s per-element reachability snapshot, the mid-press mount/unmount protection it corrected a flawed shared-boolean version of, `handleRowPointerDown`'s own bubbling wiring, `setPointerCapture`'s `try`/`catch` — still runs exactly as before, unmodified, on every breakpoint including mobile. Hiding a subtree via CSS doesn't stop React from evaluating it or firing its effects: the three buttons' own JSX conditions still read `frozenReachability`/`canReachHalfHeight`/`canReachFullHeight`/`isAtHalfHeight`/etc. on every render regardless of viewport width — confirmed live via Playwright, both breakpoints: below `min-[993px]`, the 50%/100% buttons are still *present* in the DOM (`count: 1` each, whenever reachable) but not visible or hit-testable; at/above it, unchanged from before this change. The grip itself carries no new responsive class at all — dragging it produces the identical height change (160px → 220px on a 60px drag) on both sides of the breakpoint. **The generalized tell: "remove a UI affordance on mobile" and "remove the logic behind it" are two different asks — satisfying the first by hiding rendered output via a stable, width-based CSS breakpoint leaves every behavioral fix already built for that logic fully intact, since nothing about *why* a button is or isn't reachable ever depended on whether it happens to be visually hidden by an ancestor.**

### `blockScrollThrough`'s dialog exclusion was a whole-subtree exemption, not a scrollable-area one — sticky mode leaked scroll to the page through non-scrollable dialog chrome

Reported live: with the edit dialog open on a short/narrow viewport in sticky mode, scrolling over the section tab strip — most reliably reproduced with only one tab populated — moved the *page* behind the bar instead of doing nothing, and the same leak showed up over the dialog's own borders/padding, both the "browse" (tag-grid) area's and the tab row's. Not reproducible in non-sticky mode, which is itself a clue: in normal flow the bar and the page scroll together, so there's no separate page position for a leaked gesture to reveal — sticky is what makes the leak visible at all.

Root cause: `blockScrollThrough`'s own exclusion for "let this bar's genuinely scrollable areas keep scrolling internally" was keyed off `dialogRef.current?.contains(target)` — but `dialogRef` wraps the *entire* `TagPoolBody`, not just its two actually-scrollable regions (the chip area, the section tab strip). Anything else in that subtree — the tab strip when there's no horizontal overflow to internally consume the gesture, the dialog's own border/padding pixels — matched the same blanket check and skipped `preventDefault()` with nothing else standing in for it, so the gesture chained straight through to the real page underneath. `ScrollFadeArea`'s own `overscroll-x/y-contain` classes (see its own section above) didn't save this, because they're deliberately axis-scoped per instance — the tab strip only contains *horizontal* overscroll, since it only ever scrolls horizontally — so a *vertical* gesture over it was never touched by that CSS at all, on either side of this bug.

Fix: `ScrollFadeArea`'s own scroll viewport now stamps itself with `data-scroll-fade-orientation="horizontal" | "vertical"` (its own `orientation` prop, just exposed as a DOM attribute reachable from a distant caller that only has an event target, not a ref to this component's internals). `blockScrollThrough`'s dialog-wide exemption is gone, replaced by one `target.closest("[data-scroll-fade-orientation]")` lookup used uniformly for every `ScrollFadeArea` instance on the bar (the filters row, the chip area, the tab strip alike — the filters row previously needed its own separate `filtersScrollRef` for this same axis-lock, now folded into the same generic check and removed). A gesture is let through only when its own axis matches that specific instance's orientation, exactly the same axis-derivation (`WheelEvent`'s real `deltaX`/`deltaY`, or a locked-on-first-move axis for `touchmove`) the filters-row exclusion already used — anything that doesn't land inside a marked viewport at all (borders, padding, a single-tab row's orthogonal axis) now correctly falls through to `preventDefault()`, matching every other non-scrollable part of the bar. **The generalized tell: an exclusion meant for "this element's own scrollable descendants" must be scoped to the scrollable elements themselves (or a marker they carry), not to a structural ancestor that happens to contain them alongside a lot of other, non-scrollable content — the ancestor's boundary and the scrollable region's boundary are two different shapes, and treating them as the same one exempts everything in the gap between them.**

**The JS fix above was still incomplete on its own, confirmed live on a real device: the page's own content stopped visibly moving, but touching non-scrollable dialog chrome (padding, borders, the tab strip) still visibly engaged the page's native touch-scroll first.** `blockScrollThrough`'s `preventDefault()` runs in a `touchmove` handler — necessarily a script reaction to an event the browser has already dispatched — but a real touch's native pan/scroll recognition happens at the compositor level, evaluated (via the CSS `touch-action` property) *before* JS gets a chance to run at all. A JS-only fix, however axis-correct, is always racing that native recognition rather than actually preventing it from starting; `preventDefault()` stops the resulting scroll from *completing*, but by then the browser has already begun recognizing/animating a gesture the app never wanted recognized in the first place, and real hardware apparently doesn't always lose that race the same way this file's own earlier scroll-chaining tests (which only checked `event.defaultPrevented`, a purely-JS signal, not real native touch behavior) implied.

Fix, the same "belt and suspenders, don't rely on one layer of defense" approach the resize grip already uses for its own drag (`touch-action: none` alongside its `preventDefault`, see that control's own comment): `touch-none` (`touch-action: none`) is now the bar's own root-level default (`cardRef`'s className) — the whole bar, browse or edit mode, never lets a touch starting on it be recognized as a native page-pan at all, at the CSS level, independent of any JS timing. Each `ScrollFadeArea` viewport carves its own single axis back out directly on itself (`touch-pan-x`/`touch-pan-y`, matching its `orientation` prop, right beside its `overscroll-x/y-contain` classes it already had for the same per-axis reasoning) — confirmed live via a real CDP touch dispatch (not just a synthetic `dispatchEvent`, which doesn't reliably exercise a browser's native touch-action/gesture-recognition path at all) that a descendant's own explicit `pan-x`/`pan-y` still works correctly even nested inside a `touch-none` ancestor: `touch-action`'s effective value for a touch is resolved starting from the element that touch actually lands on, not force-inherited down from a `none` ancestor, so the chip area and tab strip both kept scrolling internally exactly as before while every non-scrollable inch of the bar around them — borders, padding, the tab row's own orthogonal axis — now genuinely can't be recognized as a page-scroll gesture in the first place. **The generalized tell: for anything a touch must never be allowed to turn into (a native pan/zoom/scroll), prefer `touch-action` (evaluated pre-JS, at the level the gesture is actually recognized) as the primary defense over a `touchmove` handler's `preventDefault()` (a reaction to a gesture the browser may have already started recognizing) — reserve the JS layer for gestures a device might arguably want to allow but where an app-specific policy decision (e.g. which axis, or which registered scroll container should consume it) can't be expressed in CSS alone.**

### A defensive guard for `fixedOverheadPx`/`growableFixedOverheadPx` against rapid editMode toggling

Reported live: repeatedly tapping an empty slot fast enough (each tap now toggles edit mode open/closed — see the ADD-TAG-closes-edit-mode behavior above, which made this a new, easy way to trigger many open/close cycles from a single, unmoving tap target) could leave the edit sheet visibly misaligned. Not reproduced despite real effort — loosely-spaced clicks, maximally tight back-to-back clicks, and real CDP touch dispatch (with and without a prior sticky-then-unstuck scroll cycle first, matching the user's own repro steps) all settled to a state pixel-identical to a clean single open every time this was tried.

Even without a confirmed repro, code reading surfaced a real, principled gap worth closing defensively (the same "apply a targeted fix for the leading hypothesis, ask the user to confirm on-device" approach this session has used before for other mobile-only timing issues that wouldn't reproduce headless): both `fixedOverheadPx`'s and `growableFixedOverheadPx`'s measurement effects (`useLayoutEffect`, gated `if (!editMode) return`) create a fresh `ResizeObserver` on every `editMode` transition to `true` and `.disconnect()` it on the way back to `false` — but a `ResizeObserver` callback is asynchronous, and `.disconnect()` isn't specified to guarantee an already-queued-but-undelivered callback is retroactively cancelled on every engine. Toggling `editMode` faster than that queue drains (exactly what rapid re-tapping the same slot now does) opens a window where a callback from an *older*, already-disconnected instance could still fire — and since `measure()` in both effects reads live DOM state at *call* time, a callback firing while `editMode` has since gone back to `false` would measure a collapsed dialog/resize-row (near-zero height) and commit that as the new overhead, corrupting `poolPanelMaxHeight` and everything computed from it, until the next legitimate measurement overwrites it.

Fix: `editModeRef`, the same live-mirroring-ref pattern `effectiveHeightPxRef` already uses just above it for an identical reason (a closure only sees whatever a value was at creation time; a ref kept current via a deps-less `useLayoutEffect` reflects whatever it's actually become by the time an async callback asks). Both `measure()` functions now bail out if `editModeRef.current` is `false` at the moment they actually run, regardless of what `editMode` was when that specific effect instance was created. Declared before either effect's own first read of it (not just before its own write effect) — the project's stricter React Compiler lint rule (`react-hooks/immutability`) flagged the ref write when it was declared *after* an earlier reader in the file, even though the two are equivalent at runtime (a closure captures the enclosing scope regardless of textual order; only the *call* — always later, from an async callback — needs the binding initialized) — worth remembering as its own quirk: this lint rule's static analysis is sensitive to declaration order in a way plain JS execution order isn't, so a ref meant to be read by an *earlier* effect needs to be declared above it, not just above where it's written.

### The real mechanism behind the "mashing an empty slot glitches everything" report: a transient `marginTop` overshoot forcing a scroll-position discontinuity — plus a downstream, browser-hosting-specific compositor desync

The `editModeRef` guard above turned out not to be the actual fix — confirmed once more detail came in: the report was Chrome-on-iOS specific (didn't reproduce in Safari on the same phone, in either orientation), and a *separate*, cross-browser symptom pointed at the real trigger: rotating to landscape, scrolling to the page's true bottom (non-sticky), then opening edit mode auto-scrolled the page back up into sticky range — in both Safari and Chrome. Reproduced directly via Playwright (real CDP touch dispatch, a landscape 812×375 viewport, scrolled to `document.documentElement.scrollHeight`, one tap on an empty slot) — not a guess.

Root cause, confirmed via `requestAnimationFrame`-gated sampling of `cardMarginTop`/`scrollHeight`/`scrollY` across the transition: opening edit mode settles `fixedOverheadPx` and `growableFixedOverheadPx` across *two separately triggered commits*, not one (see those states' own comments) — and on the very first-ever open, the first of those commits still uses `EDIT_MODE_FIXED_ROWS_HEIGHT`, a worst-case *narrow/portrait* bootstrap constant, as `fixedOverheadPx`. On a wide/landscape layout that constant wildly overestimates the real overhead, making that one commit's `marginTop` far more negative than its own final, corrected value — measured live: `-385.5px` against a final, correct `-90.125px`. `document.documentElement.scrollHeight` dips correspondingly (measured: `631` against a final `926`) for that same one frame. Invisible in the ordinary case — there's slack scroll room above — but a user already scrolled to the document's *true bottom* (exactly what "scroll to the bottom, tap an empty slot" is) gets their `scrollY` forcibly clamped down by the browser to fit that transient, too-small height, and it never bounces back once the correct, taller height lands a frame later — browsers don't retroactively scroll you back down just because more room became available. This single mechanism fully explains the reported auto-scroll-into-sticky-range behavior.

It's also, very plausibly, the trigger for the Chrome-iOS-specific "everything glitches" report: a sudden, forced, *non-gesture* scroll jump — exactly what a hard clamp is — is precisely the kind of discontinuity a compositor's incremental layer-position update logic can lose track of, especially for a `position: sticky` element (commonly its own composited layer) changing size in the very same frame. A generalized version of this was independently proposed and converged on with real evidence: DevTools' own element-highlight overlay (on the user's phone, via remote Web Inspector) was seen visibly offset from the actually-painted "ADD TAG" box right after a glitch, snapping back into alignment once the page was scrolled again — a live, first-party confirmation that *layout/hit-testing* and *paint* had genuinely diverged, not just a vague "it feels off." Safari reportedly self-corrects on the next scroll (paint catches back up to layout); Chrome-on-iOS reportedly sometimes doesn't. Both browsers host the same underlying WebKit engine on iOS, so this asymmetry is most likely about how each browser's own shell integrates with WebKit's scroll/compositor pipeline (Chrome brings its own additional UI/gesture layers on top) — not something application code can directly control. What application code *can* control is not handing the compositor that sudden, discontinuous jump to mishandle in the first place.

Fix, deliberately not a rewrite of how `fixedOverheadPx`/`growableFixedOverheadPx` settle (a deeper change there carries more risk to the drag-resize behavior those two states are otherwise carefully tuned for, for a bug that only ever surfaces in this one specific corner): restore the *position*, not the transient frame's accuracy. A continuously-updated `wasAtDocumentBottomRef` (a plain `scroll`-event listener, not a one-shot capture threaded through the tap handler) records whether the user is at the document's true bottom; a `useLayoutEffect` keyed on `editMode` checks it the instant edit mode opens, and if true, pins `window.scrollTo(0, scrollHeight - innerHeight)` across a handful of `requestAnimationFrame` ticks (comfortably past the single-frame settle time this was confirmed to actually need, short enough to never fight a genuine new scroll gesture of the user's own). Confirmed live via the same frame-by-frame sampling: `scrollY` still dips for one frame, then is pulled back to the correct new bottom (`551`, not stranded at `256`) and holds there. **Removing the sudden scroll-position discontinuity this way should also remove the apparent trigger for the downstream compositor desync in both browsers — worth the user re-confirming on-device, since Chromium (dev or prod, this session tried both) never reproduces Chrome-for-iOS's own WKWebView-hosted compositor behavior regardless of how the trigger is fixed.**

A second, unrelated bug found chasing the same report: `SectionTabStrip`'s own active-tab-into-view effect used a plain `scrollIntoView({ inline: "nearest", block: "nearest" })` on the tab button, on the assumption that `"nearest"` meant "never scroll this axis" — it doesn't; it means "scroll whichever nearby container *can* move on that axis, by the smallest amount that satisfies it," and if *nothing* between the button and the document is vertically scrollable (true here — this strip's own `ScrollFadeArea` viewport is horizontal-only, `overflow-y: hidden`, and nothing above it sets any vertical overflow either), the browser keeps walking up and scrolls the whole *page* to satisfy it. Confirmed live as a second, independent contributor to the exact same class of bug: a short/landscape viewport can leave the tab strip positioned above where the page is currently scrolled once edit mode's content grows, and `scrollIntoView` then smooth-scrolls the entire page to reveal a button nobody asked to bring into view — worse than a jump, since a `"smooth"` animated page scroll left mid-flight is a moving target for whatever tap lands next, which independently explains taps registering against the wrong row entirely. Fixed by doing the only adjustment this strip ever needed — horizontal — by hand, against its own known scroll viewport (found via `data-scroll-fade-orientation="horizontal"`, the same marker `blockScrollThrough` above already uses to identify a `ScrollFadeArea` instance from outside it, without needing a ref `ScrollFadeArea` deliberately doesn't expose), instead of letting `scrollIntoView` improvise an axis this strip was never supposed to touch.

### `overflow-anchor: none` already covers scroll-anchoring, but not this

Worth ruling out explicitly, since it's the other classic cause of unwanted page-scroll-on-layout-change: `html, body` already carry `overflow-anchor: none` (see that rule's own comment, above — added for RecommendButton's spinning star). That's a real, blanket disable of the browser's own scroll-anchoring for the whole document, so it isn't what's responsible for either bug on this page — both trace to genuine, deliberate scroll calls/clamps (the forced clamp above, and `SectionTabStrip`'s own `scrollIntoView`), not the browser silently anchoring on its own.

### Cosmetic: the page's own scrollbar flashing briefly while a gesture is blocked over the bar

Reported after the touch-action fix above landed: the *functional* scroll-through block was confirmed working (page content genuinely doesn't move), but the page's own native scrollbar could still visibly flash/engage the instant it received wheel input over a blocked area (the tab strip, dialog padding) — cosmetic only, but a real, distinct symptom from the scroll-through itself. Likely the browser showing its own "yes, this page has scrollable content" affordance purely on receiving compatible input, independent of whether that specific gesture actually moved anything — `touch-action` doesn't reach this (it governs touch-panning recognition, not a wheel-triggered scrollbar affordance), and there's no scroll-*chaining* happening here for `overflow-anchor`/`overscroll-behavior` to intervene in either.

Fix: `html.hide-scrollbar-while-blocked { overflow: hidden }`, toggled by `blockScrollThrough` itself — added the instant a gesture is actually blocked (right alongside its own `preventDefault()` call), removed ~200ms after the last blocked event (re-armed on every one, so a sustained attempt stays hidden for its whole duration rather than flickering per wheel tick). Wheel input is synchronously dispatched to JS *before* the browser commits to any default action (unlike touch's own compositor-level pre-recognition, which is why `touch-action` was needed there instead) — so this has a real chance of working for wheel specifically, unlike the touch case. Confirmed live: the flash is gone.

**A first version of this also added `scrollbar-gutter: stable` on `html`, specifically so toggling `overflow` on/off could never reflow the page's own content width — reverted, confirmed live as a real, separate regression, not a fix.** iOS (Safari and Chrome, same underlying engine) uses an *overlay* scrollbar by default — it never reserves permanent layout space at all, appearing as a floating indicator only during active scroll — so `scrollbar-gutter: stable` was the thing that actually introduced a persistent, always-visible track/gutter strip along the edge that hadn't been there before, reported as the scrollbar's own color looking permanently semi-translucent/dark rather than its normal appearance. The width-reflow this was guarding against only applies to non-overlay-scrollbar platforms (classic Windows-style, or macOS with "always show scrollbars" enabled) — a narrower, rarer case than "introduces an always-visible artifact on the primary target platform," so it isn't worth guarding against here. **Same standing lesson as the last time this exact property was tried and reverted on this project (see that rule's own comment, a different reason but the same shape): a defensive CSS addition meant to prevent one hypothetical layout shift is still a real, unconditional visual change on every platform, including ones that were never at risk of the shift it was guarding against — worth checking what the *primary* target platform's own default behavior actually is before adding a permanent guard against a risk that platform doesn't share.**

### Close behaviors (every device) and focus management

**Esc and click-outside** close edit mode on every device — mobile and desktop alike, not gated to any one input type. `MixerBar` tracks its own root via a ref; while `editMode` is true, a document-level `keydown`/`mousedown` listener closes on Escape or on any click/tap outside that ref — a real Esc keypress or an outside tap both naturally produce the browser events this listens for regardless of device, so no explicit pointer/viewport check is needed either way. (The resize handle *is* desktop/pointer-only by design — don't confuse the two.) The close callback is read through a ref (updated in its own effect, not written during render — see below) rather than being a direct effect dependency, so the listener doesn't get torn down and re-attached on every render while editMode is true — props like `slots`/`dragOverIndex` change on every drag-hover tick, which would otherwise churn a document listener on every dragover during a chip drag.

**"Outside" excludes the entire main page content column, not just the bar itself** — confirmed as a real gap, not a hypothetical: clicking the theme switcher, the Results header's Clear✕, or anywhere on a result card (a tag chip, the lock/swap icons, flipping the card) all closed edit mode as an unwanted side effect before this fix, each with its own legitimate action that has nothing to do with dismissing the sheet. `KonomiApp`'s content column carries `data-konomi-content`; the click-outside check now excludes anything inside that element in addition to the bar itself (`mainContent?.contains(target)`), so only a click that lands truly outside both — the page's own background/gutters — counts as "outside." One shared exclusion zone, not four individually special-cased controls: any future control added anywhere inside that column is covered automatically, without needing its own carve-out.

**Focus moves into the pool panel on open, and back to whatever triggered it on close.** The pool panel carries `role="dialog"`, `aria-modal="true"`, `tabIndex={-1}`; on the `false→true` edge of `editMode`, an effect captures `document.activeElement` and calls `.focus()` on the dialog container. On the reverse edge, it calls `.focus()` on the captured element. **This is visually modal, not behaviorally trapped — Tab still cycles through the rest of the page, not just the panel.** No dialog library exists in this project to lean on, and there's no existing focus-trap precedent to extend; this is an accepted, explicit v1 gap, not an oversight.

*(A small, general React lint note, not specific to this feature: writing to a ref during render — `ref.current = value`, inline in the function body — trips `react-hooks/refs`. The fix used throughout this bar is to write it inside a plain `useEffect(() => { ref.current = value; })` with no dependency array, which runs after every render without the "accessed during render" violation.)*

### Why `RecommendButton` no longer needs `min-h-[92px]` or `self-start`

Both were leftovers from an older layout, where `RecommendButton` sat in its own row directly beside the tag-slots column and needed to visually match that column's height (`min-h-[92px]`, exactly a `TagSlot`'s height) and top-align to it (`self-start`). Neither reason applies anymore — `RecommendButton` lives in the controls row next to MIN TAG MATCH/Random/Clear, none of which are anywhere near 92px tall (confirmed live: `Random ×3` measures 44.5px).

Leaving `min-h-[92px]` in place after the move caused a real, non-obvious bug: it forced the *entire controls-row flex line* to 92px tall for cross-axis purposes, and centering the much-shorter MIN TAG MATCH/Random/Clear controls within that tall invisible box left roughly 26px of dead space both above and below the actually-visible controls — stacking with the real token-based row-to-row gaps on both sides to make them read as almost double their real value. This was reported and diagnosed as "the top padding is ~22px, the bottom is ~48px, is there padding not being accounted for" — the token values were correct throughout (confirmed via direct `getBoundingClientRect` measurement: both real gaps were exactly equal), the extra was entirely this invisible centering slack. Removing both `min-h-[92px]` and `self-start` lets the wrapper's height fall out naturally from its one in-flow child (the `<button>` itself — the star layers and error hint are all `absolute`, so they don't contribute), matching its row-mates and collapsing the dead space entirely.

### The spinning star is allowed to overflow past the card, on both axes, by explicit decision

`RecommendButton`'s star (two stacked, independently-rotating squares, `w-[128px] h-[128px]` and `w-[118px] h-[118px]` — shrunk down from an original 150px/139px) is absolutely positioned and centered on the small in-flow `<button>` alone, which renders far narrower and shorter than either square. The button's own wrapper carries no `min-w` (would just become invisible padding once something right-aligns the wrapper instead of the visible button — confirmed live, it left the button ~18px short of flush against `MatchSelector`'s edge), and the bar itself carries no `overflow-hidden` either.

An `overflow-hidden` clip was tried briefly, to fix what looked like an asymmetric top/bottom padding: the star's rotating axis-aligned bounding box (largest at 45°/135°/etc., where it reaches the rotated square's diagonal) breached the bar's own bottom edge at certain rotation frames — while the same overflow upward landed harmlessly inside the tag-slot row above, since there was much more clearance there. Clipping fixed the visual symmetry, but the real fix turned out to be the `min-h-[92px]` removal above (the actual padding values were never unequal) — once that landed, the clip was removed again by explicit request: the star overflowing past the bar on every side, same as it's always been allowed to overlap the tag-slot row, is the intended look, not a bug to contain. Shrinking the star (150/139 → 128/118) was the actual mitigation for "it reaches too far," not clipping.

### Divider and RECOMMEND-wrap thresholds are tied to real, external breakpoints — not re-bisected guesses

Two independent breakpoint systems are at work in the controls row, and it's important they don't get confused for one another:

**MIN TAG MATCH's label** (`hidden @min-[480px]:inline`) uses a **container query** scoped to the bar's own box width (`@container`, on `cardRef` itself — see "The single box that grows" above) — this one's purely about whether the controls row's *own* content fits, nothing external, so measuring the bar's own box is correct.

**The divider** (`hidden min-[993px]:block`) uses a **plain viewport media query** instead, and is deliberately pinned to exactly **993px** — the same number `ResultCard` already uses for its own carousel tier boundary (see below): the width where the Recommendations carousel drops from showing 4 comfortable cards to 3. The divider disappearing at that same, already-meaningful width means `MixerBar` and the Recommendations carousel change register together as the page narrows, instead of two unrelated numbers drifting in and out of sync. (An earlier version bisected the divider's own hide-point against the row's content directly — landing on 630px — but that number had no relationship to anything else on the page and was replaced.)

**A third tier softens the transition once the divider is gone**: below 993px, RECOMMEND would otherwise sit right on Clear with only the row's bare `gap-x` (12px) between them. `min-[686px]:max-[993px]:ml-[var(--space-lg)]` restores a bit of breathing room in that range. 686px isn't arbitrary — it's the bisected width at which that extra 12px margin is exactly what's needed to keep the row on one line (add the margin, and the natural wrap point moves from 674px out to 686px; removing the margin below 686px gives that width back, letting the row keep fitting all the way back down to the original 674px boundary) — the same "shed decoration before wrapping" idea the divider itself already uses, applied one level deeper.

**RECOMMEND right-aligns only once it actually wraps to its own line**, via `max-[674px]:ml-auto` — bisected live as the exact width below which RECOMMEND is guaranteed to be alone on a wrapped second line. This single fact is what makes the auto-margin safe: CSS only splits a line's free space between *auto margins sharing that same line* — below 674px, Random+Clear's own `ml-auto` is on line 1 and RECOMMEND's is alone on line 2, so the two never compete. The first attempt applied `ml-auto` to RECOMMEND unconditionally (no width gate), which worked fine once wrapped but broke the wide, single-line case: sharing a line with Random+Clear's `ml-auto`, the two auto-margins split the available free space roughly in half, visibly pulling the whole Random/Clear/divider/RECOMMEND cluster off the right edge toward the row's center — reported as "the random and clear go toward center instead." Gating the second `ml-auto` behind the same `max-[674px]` that guarantees isolation fixes it: the class simply doesn't exist on the wide line at all.

**This bug has now bitten twice, from two different causes — the lesson is about scope validity, not just "don't put two `ml-auto` on one line."** The first time (above) was RECOMMEND gaining its own icon-only fallback, which moved the wrap point and left the divider's stale 674px gate mismatched against the new content. The second time was the Tag Pool button being given its own `max-[408px]:hidden` collapse rung: the Tag Pool + RECOMMEND wrapper's `ml-auto` had been scoped to `max-[474px]` on the assumption that Tag Pool was always present on that line — once Tag Pool itself started disappearing at 408px, that assumption silently broke, and the *same* symptom came back (this time fixed by narrowing the gate to `min-[408px]:max-[474px]:ml-auto`, so the auto-margin switches off in the exact range where Tag Pool is gone and Random/Clear's own `ml-auto` is what should dock the remaining cluster). Neither incident was "two `ml-auto` classes existed at once" in the source — each scoped margin was written correctly *for the row's content at the time*. What actually broke both times: **a scoped `ml-auto`'s breakpoint is a claim about what else is on that line, not just about viewport width** — it stays correct only as long as nothing upstream of it (a new icon fallback, a new hide rung, anything that changes what's rendered at a given width) changes the row's content within that scoped range. Any future rung added to this row — collapsing another action, hiding another label — needs to re-check every existing `ml-auto`/auto-margin gate on that same line, not just add its own breakpoint and assume the others still hold.

**`MatchSelector`'s three segments show a hover/focus subtext below the whole control**, same pattern as `ThemeSwitcher`/`LevelSelector` — `"match 1+ tag"` / `"match 2+ tags"` / `"match all 3 tags"` (the last says "all 3," not "3+" — with only 3 slots total they're the same requirement, and "all" reads more naturally for the ceiling option).

**Badge background *and* text color reflect fill state**, matching the drop-tag boxes' own empty/filled distinction: `bg-[var(--slot-empty)] text-[var(--disabled-text)]` (matching `RecommendButton`'s own disabled surface/label color) at `0 / 3`, `bg-[var(--fill)] text-[var(--ink)]` (matching `Random ×3`'s own bg/text) from `1 / 3` up.

## Mixer error system, and why there's no live filtering at all

**`RecommendationsBody`'s placeholder box renders on `!hasResults`, not `empty` (`!generated`).** An error still sets `generated: true` (see `recommend()` below) while leaving `results` untouched — on a first-ever RECOMMEND attempt (or right after Clear ✕), `results` is already `[]`, so the moment an error fires, `empty` goes `false` (generated is now true) *and* `hasResults` stays `false` (still zero results) — a third state the original `empty`/`hasResults` two-way branch never accounted for. With the condition as `empty`, that state rendered neither the placeholder nor the results grid, collapsing the whole section down to just its header, then jumping back to full height the moment a real result set finally loaded — reported as "the placeholder disappears completely, we don't want a jarring height change." `!hasResults` covers both "never generated" and "generated but errored with nothing to show," so the placeholder (and the `--result-card-height` it reserves) stays put across an error the whole time. The now-redundant `empty` field was removed from `useKonomi`'s return value and the prop chain entirely, rather than left unused.

**The displayed result set is always exactly `state.results` — there is no filtered/derived view sitting in front of it.** An earlier version of this app had a `visibleResults` layer that hid stored entries live based on min-match (frozen `entry.score` vs a live threshold). That's been removed entirely: it turned out to be the wrong model. The actual requirement is simpler and stricter — **only RECOMMEND and Clear ✕ change what's visible.** Adjusting MIN TAG MATCH or changing/swapping/removing tags never hides or shows a card; they only change what *setting* the next RECOMMEND will use, and (for tags) what each already-visible card's live score badge and highlights show. Remove every tag down to zero and every card stays put, honestly showing `0/0` — nothing to hide, because hiding isn't a thing tag or min-match changes do anymore.

This means `entry.score` (the field stored on each `ResultEntry`) is now purely informational — nothing reads it to decide whether a card is shown. The only score that ever drives anything a user sees is the *live* `scoreSeries(series, selectedTags)` call inside `ResultCard`, used for the count badge and tag highlighting, recomputed fresh on every render regardless of what's stored. Because there's no visibility filter left to satisfy, the locked-carry-forward path in `recommend()` no longer needs to clamp its score to the current min-match either (see below) — it's just the honest live score, kept only for whatever informational value it has.

**`state.error` — reducer state, set only by RECOMMEND, cleared only by specific actions.** This can't be a derived value — if it were computed live from `tagCount < minMatch`, it would flicker on/off automatically as tags or min-match change, which directly contradicts "errors fire only on RECOMMEND." So it's real state (`MixerError = "impossible-min" | "no-match" | null` in `types.ts`), mutated by exactly one reducer function (`recommend()`, which sets it) and a handful of specific clearing rules elsewhere. On either error, `results` is deliberately left completely untouched.

**Priority order inside `recommend()`, checked in this sequence every time:** first `sel.length < min` → `"impossible-min"` (never touches the catalog at all); else run the real `scorePool` rescore, and if it comes back empty → `"no-match"` — checked as `pool.length === 0`, not `out.length === 0`. This distinction matters: locked cards surviving in `out` doesn't mean the error shouldn't fire, since the error is about whether a *fresh* search for *new* matches succeeded, which is an entirely separate question from whether anything old is still on screen. A `RECOMMEND` can legitimately show "no series match this mix" right next to two locked cards that are still sitting there from before.

**Clearing tracks current state, not which action originally triggered the error.** `"no-match"` clears on *any* tag or min-match change — the whole combination was the problem, so any edit is a fresh attempt worth trying again. `"impossible-min"` clears whenever the underlying condition (`tagCount < min`) stops being true, from either side: `SET_MIN_MATCH` lowering the threshold to `<= tagCount`, *or* `clearErrorForTagChange` seeing `tagCount` rise back to `>= min` (a manual tag add, or Random ×3 refilling all slots) — both are handled, not just the min-match-control path. The first version of this only cleared on the min-match side, which left a real gap: erroring at min-3 with 2 tags, then adding a third tag, should obviously clear it (2 tags making min-3 impossible has stopped being true), but nothing re-evaluated the error until the user touched MIN TAG MATCH itself. `clearErrorForTagChange` also still handles the separate global-override case — tag count dropping to exactly zero clears either error type, since `min-match` can never be lower than `"1"`, so `tagCount >= min` is never satisfied by zero tags on its own; the zero-tags case needs its own explicit check. Called from every slot-mutating action (`TOGGLE_TAG`, `CLEAR_SLOT`, `PLACE_IN_SLOT`, `CLEAR_SLOTS`, `PRUNE_TAGS`, `RANDOM_TAGS`).

**`SET_MIN_MATCH` no longer calls `recommend()`.** It used to cascade a full rescore whenever results were already showing. That's now handled entirely by live filtering (which needs no reducer action at all) — the reducer's job on a min-match change is just to update the value and apply the two clearing rules above, nothing else.

**Visual treatment reuses the existing disabled styling, but decouples two conditions that used to be one.** `RecommendButton`'s star has always dimmed to `opacity-35` when disabled (unchanged, still tied to `!enabled`, now `enabled = filledCount > 0 && !error`). What's new: the star's *rotation* is tied to a different condition (`!error`, not `!enabled`) — so the pre-existing zero-tags state still dims while continuing to spin (unchanged behavior), but an active error additionally freezes it, giving the two disabled states a distinct feel even though they share a color treatment.

**Freezing uses `animation-play-state`, not adding/removing the animation class.** An earlier version toggled the whole `animate-[kono-spin_…]` class off on error, which stops the animation by dropping its `transform` entirely — the star snapped back to its base 0deg orientation on every error, then jumped again on resume, instead of pausing wherever it happened to be mid-spin. The animation class now stays on permanently; only `[animation-play-state:paused]` / `[animation-play-state:running]` toggles with `error`. Pausing a CSS animation freezes its current computed transform in place (the browser already tracks elapsed animation time — no manual angle capture needed), and un-pausing resumes from that exact point rather than restarting. Verified live via `getComputedStyle(el).transform`: the paused matrix stays byte-identical across an 800ms wait, and the first frame after resuming shows a small delta from the paused matrix rather than a jump back to the identity matrix.

**Star size (150px outer / 139px inner, previously 190px / 176px) is a plain visual-weight reduction** — the two layers keep the same ~0.93 size ratio to each other, just scaled down together.

**The upward-shift layout is a precise formula, not a guessed offset.** The star+button assembly sits in a `min-h-[92px] flex items-center justify-center` box; adding a taller subtext below and letting the box grow would leave the button pinned at the top (`items-start` in the row above already fixes that edge), not shifted up. Instead, `RecommendButton` applies a `translate-y` to the star+button wrapper (Tailwind v4 note: individual translate utilities compile to the native CSS `translate` property now, not `transform` — check `getComputedStyle(el).translate`, not `.transform`, when verifying) and renders the subtext `position: absolute, top-full`, matching the same out-of-flow hint pattern used for `LevelSelector`/`TagPool`'s hints elsewhere in this file. The shift amount is `(gap + subtextLineHeight) / 2` — half of what's being added below — which is exactly the offset that makes the *new* block (button + gap + subtext) center on the same point the button *alone* used to occupy in that fixed 92px box. Measured live: `9.5px` (`4px` gap + `15px` line height), verified to a `0px` diff between the box's natural center and the shifted block's center.

**The old "no series match that strict" banner in `RecommendationsBody` is retired.** It's now redundant with the button-adjacent error message. `hasResults`/`empty` keep their prior meaning (`generated && results.length > 0` / `!generated`); there's no longer a distinct banner for "generated, but currently nothing to show" — that state (which can now only happen right after an errored `RECOMMEND`, since a *successful* one always produces at least one result) is deliberately blank in the grid area, since the error message at the button already explains it, and duplicating that explanation with slightly different copy would be more confusing than nothing.

### Locked cards are real, positioned members of `results` — not a visual overlay

**`recommend()` walks the raw stored order directly, and that's correct — not a simplification that cuts a corner.** An earlier version of this logic walked a separately-filtered "current visible" list instead of `state.results`, because at the time a card could be hidden live (by min-match) while still being stored — meaning stored order and displayed order could diverge, and a locked card could visually "jump" position across a RECOMMEND if the loop walked the wrong one. That entire divergence is gone now that there's no live filtering at all (see the section above): the displayed set *is* `state.results`, always, so there is no separate "visible order" left to reconcile against. Walking the raw array directly is therefore the *correct* model again, not a reversion that reintroduces a bug — the bug it used to cause can't occur without the live-filtering layer that originally created the mismatch.

**Relative order + compaction still falls out of the loop shape for free, unrelated to any of that.** `recommend()` walks `state.results[i]` for `i` in `0..DEFAULT_RESULT_COUNT`, pushing (a) the locked entry when found at that index or (b) the next fresh pool pick when one's available, skipping only when neither applies. Locked entries get visited and pushed in the same relative sequence they already had (order preserved for free), and a skipped iteration contributes nothing rather than a gap (compaction for free) — this was true before the live-filtering detour and remains true now that it's been removed.

**Locked-carry-forward no longer clamps its score.** It used to compute `Math.max(scoreSeries(old.series, sel), min)` specifically to guarantee a carried-over locked entry would satisfy the live visibility filter's `score >= min` check even after being unlocked. With no visibility filter left to satisfy, that clamp was solving a problem that no longer exists — it's now a plain `scoreSeries(old.series, sel)`, the honest live score, kept only because `ResultEntry.score` is still a field on the type (informational, read by nothing).

**`REPLACE_CARD` still targets by title, not index — this didn't need to change.** It moved to title-based targeting during the live-filtering era for a reason that no longer applies (displayed and stored order could diverge), but title is the same stable identifier `TOGGLE_LOCK`/`TOGGLE_FLIP` already use, and there's no reason to revert something that's strictly more robust just because its original motivating scenario went away.

### Mini error-hint stars — built, tried live, then deliberately removed

A `MiniStar` component briefly existed, decorating a handful of specific targets while a mixer error was active (a MatchSelector segment, RANDOM ×3, CLEAR SLOTS, the weakest filled tag slot) with a small rotating star anchored to specific text within each. After trying it live, the call was that the error subtext alone communicates clearly enough, and the extra spinning accents read as distracting rather than helpful — removed entirely (`MiniStar.tsx` deleted, `starred`/`starMaxValue` props and `weakestFilledTag` derivation all pulled back out of `TagSlot`/`MatchSelector`/`MixerSection`/`useKonomi`). Noting this so it doesn't get quietly rebuilt from scratch later: if highlighting/hinting comes up again, it's an open question worth a fresh design pass, not necessarily "bring back the mini stars" — try a different mechanism first (e.g. something less animated) rather than assuming this exact approach was just under-tuned.

**What stayed: `--primary-deep`, the new color token this feature introduced.** A bold, high-contrast variant of `--primary`, deliberately *not* derived the same way in every theme — for the two light-surface themes (default, "third"/Newsprint) it's `--primary` darkened, but for "dark"/Tide, whose surface is already dark and whose `--ink` is near-white, darkening further would move *toward* the background rather than away from it, so Tide's variant is `--primary` lightened by the same blend ratio instead. Still used for the mixer error subtext (`RecommendButton`'s `ERROR_MESSAGE` span) — that's the part of this feature that earned its keep. Defined in `ThemeColors` (`types.ts`), `THEMES` (`themes.ts`), and all three `[data-theme]` blocks in `globals.css`, the same three-places-in-sync pattern every other role-based color already follows.

## React Native portability

`src/lib/konomi/` (types, data, tokens, themes, scoring, and the `useKonomi` state hook) contains zero DOM or web-only APIs — no `document`, `window`, `HTMLElement`, or browser event types. It's plain TypeScript plus React hooks, which run the same way under React Native. The one deliberately web-only concern — HTML5 drag-and-drop — lives entirely in the web components (`TagChip`, `TagSlot`), which call into the same plain actions (`toggleTag`, `placeInSlot`, etc.) a React Native gesture handler would call.
